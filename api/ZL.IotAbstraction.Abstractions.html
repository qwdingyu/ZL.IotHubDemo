    BadcEndianConverter

    BADC 字节序转换器（字内字节交换，字间小端）。

    协议字节 [B][A][D][C] 中，先交换每个 16 位字内的两字节得到 [A][B][C][D] 的字内顺序，字与字之间按小端（低字在前）排列。

    ⚠️ 当前无生产驱动使用本类。整个 32/64 位实现在 2026-09-03 之前是错的 （TransInt32 与 BigEndianConverter 逐字符相同，等于没做 BADC 重排）， 已按 HSL DataFormat.BADC 修正并补单测。启用到任何驱动前请先在真机验证。

    CdabEndianConverter

    CDAB 字节序转换器（字内字节交换，字间小端）。

    协议字节 [C][D][A][B] 表示数值 0xABCD：每个 16 位字内按大端 （[C][D] = 字 0xCD），字与字之间按小端排列（低字在前，即 [C][D] 是低 16 位、[A][B] 是高 16 位）。

    ⚠️ 本注释 2026-09-29 修正：旧注释误写"字间大端（高字在前）"，与实现相反 （Order32={1,0,3,2} 解码为低字在前）。已用 HSL ByteTransformBase CDAB 分支 与 FATEK 真交叉测试（Float/Int32 跨字）双重验证：实现正确，注释错误。

    适用场景：汇川（Inovance）、台达（Delta）、永宏 FATEK（跨字小端）等 PLC。

    ConnectionHealthReport

    DeviceWriteDispatch

    把"按运行时类型分发到对应的类型化写入"这条规则收敛到一处。

    【为什么异步能共享、同步不能】 IPlcDevice **声明了异步的类型化写入**（WriteAsync(string, bool/short/…/double)、 数组版、WriteAsync(string, string, Encoding)、WriteBytesAsync） ⇒ 分发可以**经接口**完成 ⇒ 能共享 [OK]； 而**同步**的类型化写入**不在**接口里（只有 Write(string, object|string|byte[])） ⇒ 无法经接口分派，给公开接口补成员又是**破坏性变更** ⇒ 同步分发**消不掉** [OK]。

    【本实现覆盖的变体】对应原 AllenBradleyCipDriver / ModbusRtuDriver 两份 **逐字相同**的实现：11 个分支（bool/short/ushort/int/uint/long/ulong/float/double/string/byte[]）， 字符串固定用传入的编码（原为 System.Text.Encoding.UTF8），不支持的类型返回 Fail("不支持的类型: …")。

    【不覆盖的变体（有意）】SiemensS7Driver 多一支 byte 且有 null 检查； MitsubishiMcDriver/OmronFinsDriver 是 Task.Run(() => Write(address, value)) **一行转发到同步路径**（不是同一条规则）；NativeDriverBase/SerialDriverBase/ ModbusAsciiDriver/HttpDriverBase 各自不同 ⇒ 合并它们需要**统一语义**， 属产品决策，已在列出完整变体地图 [OK]。

    DisposeGuard

    「是否已释放」的唯一判定入口 ✓。

    【为什么需要它 ✗→✓】本仓的驱动存在**三种并行范式** ✓：

    1. 继承 NativeDriverBase（5 个驱动）✓ —— 基类只提供 EnsureNotDisposed()（**抛异常** ✗），**没有**"只判释放"的属性 ✗
    2. 继承 SerialDriverBase（5 个驱动）✓ —— 另一套平行实现 ✗
    3. 独立实现 IPlcDevice, IDisposable（9 个驱动）✗ —— **各自**声明 `_disposedFlag` 并**各自**写判定 ✗

    ⇒ 同一个问题「已释放之后该返回失败还是抛异常」在仓里曾有三套答案 ✗✓， 于是必然出现"改了 A 漏了 B、修了 7 个还剩 2 个" ✗（本项目真实发生过 ✓）。

    【本类的职责很窄 ✓】只回答"**这个标志位是否已置位**" ✓， **不碰 socket、不碰锁、不抛异常、无状态** ✓ ⇒ 可以直接用在**任何**范式里 ✓。 ⚠️ 它**不是**新的抽象层 ✗：没有接口、没有继承关系、没有依赖注入 ✓。

    【⭐ 关键纪律 ✗】**"已释放"和"未连接"是两件事，不可混淆** ✗✓ —— 本项目曾因用 `IsConnected`（同时含"未连接"与"已释放"两个条件 ✓） 去判定"是否已释放" ✗，把 `ConnectServer()` 的**正常连接流程也挡掉了** ✗， 导致 3 条 S7 用例变红 ✓。 ⇒ 需要"能否收发包"的判定用 `IsConnected` ✓； **需要"是否已释放"的判定一律用本类** ✓。

    MeterBcd

    DLT645 / CJT188 等计量表协议的 BCD 数值编解码（低字节在前）。

    这些协议的响应体是 BCD、低字节在前，且每 DI 的小数位不同。 本类把它们做对：反序 → BCD→整数 → ÷10^digit，写方向做完全对称的反算。

    典型用法（读）：

    var raw = device.ReadBytes("000000000001;02010100", 2);   // 原始字节，如 {0x11,0x23}
if (raw.IsSuccess) {
    decimal volt = MeterBcd.ToEngineering(raw.Content, decimals: 1);   // 231.1m
}

    典型用法（写）：

    byte[] wire = MeterBcd.ToWire(231.1m, byteLength: 2, decimals: 1);     // {0x11,0x23}

    [!] 本类**不做**"用户自定义换算"（乘系数/加偏置）—— 那是 ValueScale 的职责，两者语义不同，不要混用。

    NativeProtocolDescriptor

    原生协议画像：把"设备类型差异"从驱动主逻辑中剥离的策略对象。 不同 PLC 协议（西门子、三菱、欧姆龙等）在客户端创建方式、地址格式、字节序等方面存在差异。 本类将这些差异封装为可插拔策略，使 NativeUnifiedDriver 能以统一逻辑驱动所有协议。

    PlcAddress

    PLC 地址的统一归一化模型。 不论底层是西门子 DB、三菱 D、Modbus HR 还是欧姆龙 CIO， 所有地址经 PlcAddressHelper.Parse 后都会转化为本对象， 供后续的批量读取引擎（BatchEngine）和值提取器（PlcValueExtractor）使用。

    PlcAddressHelper

    多协议 PLC 地址解析器——本库的核心基础设施之一。

    将不同厂商的文本地址（如 "DB1.DBX0.0"、"40001"、"D100.3"、"CIO100.03"） 统一归一化为 PlcAddress 对象（DataBlock + TypeCode + ByteOffset + BitOffset）， 使上层的批量读取引擎和值提取器可以跨协议工作，无需关心底层地址格式差异。

    解析策略采用"正则匹配链"：按优先级依次尝试 12+ 种正则模式， 匹配成功则立即返回，全部失败则抛出 FormatException。 支持通过 PlcAddressParseOptions 指定协议画像和严格模式以消除歧义。

    PlcDataTypeMap

    PLC 数据类型映射表（唯一权威来源）。

    ── 为什么需要这个类 ──────────────────────────────────────── 历史实现在多处各自维护"类型码 → 字节长度"的 switch （PlcReadBlockBuilder.GetTagByteLength、GetTagActualBytes、 PlcValueExtractor.Extract、DeviceBase.ReadTypedAsync 等）， 这些副本**只列规范名**，别名（int16 / int32 / real / int64 …） 会落到各处的 default 分支。

    其中 PlcReadBlockBuilder 的 default 返回 1， 导致别名点位的读取块长度被算成 1 字节。危害是**完全静默**的：

    • 块长度 1 字节 → 只读到 1 字节；
    • 提取阶段 rel + 2 <= buffer.Length 不成立 → 整个标签被丢弃；
    • 不抛异常、IsSuccess 始终为 true、无告警；
    • 现场现象是"这个点位一直没有值"，排查方向会被误导到 PLC 侧。

    本类的目标是把"类型码 → 长度/规范名"收敛为**单一实现**， 任何新增类型只需在此处登记一次。

    兼容性约定：

    • 查表**大小写不敏感**（Float 与 float 等价）；
    • 未知类型**不抛异常**，由调用方决定回落行为（保持历史兼容）。

    PlcReadLengthGuard

    读长度的窄化守卫。

    【缺陷背景】点表 TagItem.Length 来自 XML（`TagItem.LoadByXmlElement` 只有 `int.Parse`， **没有任何范围校验**），而字符串读路径把它 `(ushort)` 窄化后交给驱动 （`ReadStringAsync(address, (ushort)readLength, …)`）⇒ 例如 `Length = 100000` **静默回绕成 34464** ⇒ **读错长度、返回错值，且不抛异常、不告警**。

    【为什么"响亮失败"而不是"钳位"】钳位（截到 65535）仍然是**静默读错** ✗； 而越界 `Length` 的当前行为本就是**未定义的错误值** ✗ ⇒ 换成**明确失败**属于 “消除静默错误” ✓，不是改变一个被正确依赖的语义 ✓。

    【为什么单独成类】字符串读路径有**多处**（`DevicePro`、`BatchMonitor`、 `DeviceBase`），逐处各写一遍判定必然漂移 ⇒ 统一收口到这里， 且它是**纯函数** ⇒ 可离线单测（`InternalsVisibleTo("ZL.IotHub.Tests")` ✓）。

    PlcStringKindResolver

    "标签生效 StringKind"的唯一解析点。

    【为什么必须唯一】收口前该判定在仓内**抄了 6 遍**（`DevicePro`×2 ✓、`DeviceBase`×2 ✓、 `BatchMonitor`×1 ✓、`PlcValueExtractor`×1 ✓），模式完全相同： if (kind == None) kind = DefaultStringKind != None ? DefaultStringKind : Raw; ✗ —— 同一概念多处成立，任一处漏改即分叉 ✗（本仓已多次因此出问题 ✓）。 现只在此定义 ✓，并让"驱动自述布局"只需接一次 ✓。

    PlcStringReadHelper

    PLC 字符串读取的共享 纯函数（读侧唯一解析源，与写侧 PlcStringWriteHelper 成对）。

    职责边界：只负责「把一段已经读到的字节缓冲，按 StringKind 布局与 encoding 解析成 .NET string」， 不负责传输（读几段、从哪开始读、读多长）。传输策略由各调用方决定。

    【2026-10-17 二次收口】此前"唯一解码源"只完成了 1/4 ✗： 仅 PlcValueExtractor 委托到这里，而 DevicePro.ReadStringAsync<T> 与 DeviceBase.ReadFromDeviceInternal 各自内联一套头剥离 + 解码 + 修剪 ✗， BatchMonitor.ReadStringAsync 更是"先让驱动把地址偏移 +2 拿到无头内容、再对 string 剥一次头" ✗。 实测后果：同一个 S7String 标签、同一份 PLC 数据，四条读路径给出不同的值 ✗。

    【统一口径（四条读路径共同遵守）】 ① 头剥离只发生在原始字节上，且只发生一次 —— 对已解码的 string 再剥头是结构错误 ✗； ② 内容区只按布局声明的长度取（Raw=声明长度、S7String=Byte1、S7WString=实际字数×2）； ③ 不按内嵌 \0 截断（S7 STRING 允许内嵌 NUL，按首 NUL 截会丢数据）； ④ 只做 TrimEnd('\0')（尾部填充），不去首尾空白、不删内部 CR/LF。

    PlcStringWriteGuard

    Raw 字符串写入的容量守卫。

    【为什么单独成类】仓内共有 6 处带 maxLength 的 Raw 写入点： NativeDriverBase.WriteString/WriteStringAsync、 SiemensS7Driver.WriteString/WriteStringAsync（该类直接实现 IPlcDevice，不派生自 NativeDriverBase）、 PlcDeviceStringWriteExtensions.WriteStringFallback/WriteStringFallbackAsync （服务 AB / 三菱等“裸字驱动”，直接 device.Write(byte[]) ⇒ 绕开前两者）。 若逐点各写一遍判定，阈值与提示语迟早漂移、且新增第七个写入点时极易漏判 ⇒ 统一收口到这里，判定规则与提示语只有一处定义。

    【缺陷背景】BuildRawPayload(string, Encoding, int) 的契约是 “不截断超长，由调用方决定 Fail 或截断”，而上述 6 处原先都没有判定； NormalWriteRequest.StringLength/SafetyWriteRequest.StringLength 对外文档是 “字符串最大长度（字节/字符）”，且 tag.Length 就是字段字节宽 （读侧 ReadString(addr,size) 走 ReadBytes(addr,size)；写侧短则补零到该长度） ⇒ 超长时按实际字节数写入会写穿点表 Length 界定的字段，静默覆盖其后相邻的 PLC 存储区。 兄弟路径 S7 STRING / WSTRING 一直是超长即 Fail ⇒ 本类把同一约定补齐到 Raw 路径。

    【为什么不把判定做进 PlcStringWriteHelper】该类是“平台无关的纯函数”集合， 不应反向依赖 DeviceResult；故“纯函数只负责算、是否可写由本类判定”。

    IBlockSizeHintProvider

    可选：驱动声明「本协议单次读取块的最大字节数」（2026-11-16 新增，修台账 BO）。

    【为什么需要】采集引擎的 `PlcReadBlockBuilder` 有一个**全局默认** `MaxBlockSize = 220`。 但少数协议的真实单帧上限**低于 220**（实测记录）：

    • `melsec-fx-links` **≤128 字节**（超出会被钳位，读到的比请求少）
    • `modbus-rtu-over-tcp` **≤250 字节**（实测 250 OK / 256 失败）
    • `allen-bradley` **≤256 字节**（实测 300 → 返 256，静默截断）

    ⇒ 用默认 220 请求这些协议，会发出超过其能力的块。

    【为什么是「引擎问驱动」而不是「引擎查表」】AGENTS §15.3 规定 **引擎零协议知识**（不得引入任何协议枚举/常量表）⇒ 协议上限只能由**驱动自己**声明， 引擎通过本接口**通用地**读取。这与既有的 Core.IAddressSemantics（引擎向驱动问地址语义）是**同一模式**。

    【语义约定（必须遵守）】

    1. 0 = 未声明 ⇒ 引擎沿用其配置的 `MaxBlockSize`（**行为零变化**）
    2. > 0 ⇒ 引擎取 Min(配置值, 本值) ⇒ **只收紧、不放大** （用户显式把 `MaxBlockSize` 调小仍然生效）
    3. 本值只影响**读取块的长度**，不改变单点读/写路径

    [!] 声明值必须有**实测或官方依据**并写在该驱动的实现处（AGENTS §22.5）， 不得凭印象填。填小了只损失吞吐，填大了会**读到截断数据**。

    【2026-11-05 迁入 Abstractions】原在 ZL.IotEngine.Orchestration： 契约接口按分层应归 Abstractions；且同名的 ZL.IotAbstraction.Tag.IDeviceDriver（死接口，已删除）曾导致消费者 同时 using ZL.IotAbstraction.Tag; + using ZL.IotAbstraction.Orchestration; 时裸写 IDeviceDriver 出现 CS0104 歧义。 ⚠️ 本包**尚未发布** ⇒ 迁移零兼容成本；发布后再改命名空间即为破坏性变更。

    IPlcDriver

    标准化 PLC 驱动接口（推荐）：支持异步连接、高性能缓存读取、点位写入及触发式事件抛出。

    这是项目中 PLC 通讯的核心契约。所有驱动实现（HslUnifiedDriver 等） 均需实现此接口，使上层采集逻辑与底层协议解耦。

    设计要点： - 异步优先：ConnectAsync / WriteTagAsync 均返回 Task，避免阻塞采集线程。 - 缓存读取：GetCachedValue 从内存缓存中取值，无需每次发起网络 IO。 - 事件驱动：DataCollected 事件在批量采集完成后统一推送，支持 SCADA/MES 订阅。

    IStringLayoutProvider

    可选契约：驱动自述其字符串的原生物理布局。

    【为什么需要它 —— 降低下游负担】`StringKind` 是**布局判别式**，对**协议固定**的设备 （如 AB Logix 的 `STRING` 恒为 `DINT LEN + SINT DATA`）来说，这个值是**驱动的事实** ✓， **不该**要求用户/上位机去配置 ✗。 实测下游证据：`iot-sdk` 的 `UcTagTable` 把 `StringKind` 当**布尔开关**用 （`StringHasLeader ? StringKind.S7String : StringKind.Raw` ✗）⇒ UI **无法表达**新成员 ✗ ⇒ 若把 `AbCipString` 做成"必须配置"，等于给所有下游加负担 ✗。

    【设计取舍】用**独立可选接口**而非给 IPlcDevice 加成员 ✓： · 加成员会让**所有外部实现者**编译失败 ✗（`ZL.IotHub` 是已发布 NuGet 包）； · 本接口是**增量**契约 ⇒ 既有驱动零改动 ✓、不实现者行为不变 ✓。

    【解析优先级】标签显式 StringKind > 本接口（驱动事实 ✓） > 设备配置 > Raw —— 见 PlcStringKindResolver ✓。 驱动声明**优先于设备配置**，因为对协议固定的设备，配置改不出正确结果 ✗， 让配置覆盖它只会制造"看似可调、实则必错"的旋钮 ✗。

    ⚠️ **只对"字符串布局恒定"的协议实现本接口** ✓：如 AB Logix 的 `STRING` ✓。 S7 **不得**实现 —— 其 `STRING` 与 `WSTRING` 是**变量级**选择 ✗，驱动无从得知 ✗ （那仍由点表/设备配置决定 ✓，属真正的配置维度 ✓）。

    🔴 **历史误判标注**：曾有人 grep「S7 未实现本接口」 直接定性为缺陷并开"实现 provider"的修复处方 —— **这是错的** ✗（见上方 「S7 不得实现」的明文决策；照做会破坏 WSTRING 用户）。审查/审计时若发现 「某协议未实现本接口」，**先读本段决策再定性** ✓；string 配置要求见 `docs/drivers/SiemensS7.md` 6.3.1（string 必须显式配 StringKind）✓。

    ITriggerableDriver

    可触发驱动的统一事件接口。

    实现此接口的驱动（如 Native.NativeUnifiedDriver、 Hsl.HslUnifiedDriver（由 ZL.IotHub.X 提供）、`S7NativeDriver`（ZL.IotDriver.Siemens） 等） 在采集到标签值变化时触发 TriggerDataChanged 事件。

    与 HSL.DataFormat 同名但不同命名空间，实现解耦。 西门子 S7 使用 ABCD（Big-Endian），Modbus 常用 BADC/CBAD/DCBA。

    DeviceFailureKind

    失败性质（跨协议统一）。用于下游做程序化分支（重试 / 告警 / 弃用点位）。

    🔴 设计原则：粒度只到"下游做决策所需"，不追求穷尽所有技术细节 ✗ —— 过细的分类会让驱动实现者无从判断，反而降低可靠性。

    FailureOwner

    失败的责任方（粗分类，回答"谁该来修"）。与 DeviceFailureKind 并存、不替代。

    🔴 为什么细码之外还需要粗分类： PROFINET 同时有 ChannelErrorType（细）与 ErrorCategory（粗），两者互不替代； OPC UA 也同时有 Bad（严重级）与具体状态码 ✓

    🔴 为什么不用一个布尔： 曾设计 `IsConfigurationError = Kind is ArgumentError or AddressError`， 有三个缺陷 ✗： ① 命名说"配置"，实际只含 2 个值（`Unsupported`/`Disposed` 被排除在外）； ② 把**两个不同责任方**混在一起 —— `ArgumentError` 是**调用方代码 bug**（传了 null）， `AddressError` 是**点表配置错**（地址写错），运维看到 `true` 不知改哪； ③ 布尔把 5 种原因**压平**成 1 位信息 ⇒ 下游拿不到诊断价值 ✓

    ⇒ 改为四值枚举：**保留全部诊断信息**，且能直接指导"该找谁修"✓

    PlcDataFormat

    数据格式（字节序）——定义 16/32/64 位数据的字节排列方式。

    命名约定：每个字母代表一个字节位置（A=最低字节, D=最高字节）

    ABCD大端序（Big-Endian）：D0 最高字节在最前
    DCBA小端序（Little-Endian）：D0 最低字节在最前
    CDAB字内字节交换：先交换 16 位字，再按大端排列
    BADC字内字节交换：先交换 16 位字，再按小端排列

    适用场景：汇川（Inovance）、台达（Delta）等 PLC 使用 CDAB 字节序。
