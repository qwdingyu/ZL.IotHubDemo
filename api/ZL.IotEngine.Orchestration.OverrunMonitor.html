    Class OverrunMonitor

    周期 overrun 监控器（docs/653 D2）。每台设备（每个扫描桶）一个实例。

    为什么需要：CustomPeriodicTimer 的语义是"从**绝对时间点**起算" —— 本轮耗时 > scanRate 时**下一 tick 立即返回**（不等待） ⇒ **背靠背满负荷**（是"打满"，不是"降频"）。现场只能看到"数据在动但周期不准"， **没有任何指标**说明"你要的 100ms 做不到" ✗

    为什么不放在 DeviceBase 里：那个文件已**超行数基线** （`㊲` 门禁「只减不增」）⇒ 按门禁推荐①「按职责切」抽出来 ✓

    TryGetSuggestion(int, int, out int)

    显式建议 API（docs/653 D2 的方案 C：本仓不自动改调度，只给建议）。

    为什么不自动退避：自动改 `ScanRate` 会**改变采集语义** —— 下游可能按 `ScanRate` 做控制时序；且"何时恢复"在工业现场**无法定义** （负载降了退回原值 ⇒ 又 overrun ⇒ **振荡**）✗ ⇒ 决定权交给**操作员/上层**：调 `TryGetSuggestion` 拿建议值，自己决定是否应用。

    用法：if (dev.Overrun.TryGetSuggestion(100, out var s)) { /* 决定要不要把 ScanRate 改成 s */ }
