    Class TagValue

    工业级数据载体——每个 PLC 点位的"值 + 质量 + 时间戳"三元组。

    这是整个采集系统中最基础的数据单元，类似于 OPC 中的 DataItem： - Value：从 PLC 读到的原始值（可能是 bool/int/float/string 等）； - Quality：数据质量码，标识该值的可信程度； - Timestamp：采集时刻的时间戳，用于趋势图、数据回溯等场景。

    【不可变性保证】 此类为不可变（immutable）——所有属性通过构造函数一次性设置，之后不可修改。 多线程环境下可安全共享，无需额外同步。更新值时创建新实例（copy-with-update）， 配合 ConcurrentDictionary.TryUpdate 的 CAS 语义实现无锁数据流。

    对标方案： - OPC UA .NET Stack: DataValue (Value, StatusCode, SourceTimestamp, ServerTimestamp) — 全 readonly - Beckhoff TwinCAT: PlcTag — immutable snapshot 模式 - Eclipse Milo: DataValue — 不可变 + 工厂方法

    LastError

    最后一次失败的原因（docs/653 D11）。null/空 = 无错误（Good/Uncertain 通常为 null）。

    为什么用字符串而不是新枚举：新增质量枚举会**破坏兼容** （下游 `switch (Quality)` 会漏分支 ⇒ 编译告警或运行期落空）。 字符串不改变任何既有契约，且能承载**驱动错误码原文** （如 S7 `0x81/0x04 ⇒ PUT/GET disabled`、Modbus 异常码、超时秒数）✓

    与 Quality 的关系：`Quality` 说"多可信"， `LastError` 说"**为什么不可信**"。二者独立：`Uncertain`（陈旧值）也可带原因 （如"本次超时，保留上次有效值"）✓

    Value

    点位原始值（协议解码后、未经任何用户配置换算的值）。 类型取决于 PLC 地址的数据类型（bool/short/int/float/string 等）。

    🔴 契约（docs/558）：IotHub 只提供原始值，不做工程量换算（缩放/偏置/查表）。 需要 `raw * 0.1 - 40` 这类换算时，请在**应用层/展示层**用 ZL.IotAbstraction.Utils.ValueScale.Apply/Reverse 自行处理，不要期待本值已换算。

    为什么这条契约必须守住（docs/558 §二）：

    1. 本 SDK 同时服务 SCADA 展示 与 自动化控制 两条下游， 两者对"要不要换算"的需求相反（展示要方便、控制要安全）⇒ 中间层做任何选择都会得罪一边；
    2. 原始值是唯一能自证的层：排障时变量只有"驱动解码"一个， 而不是"驱动解码 + 换算配置 + 死区"三个；
    3. 换算后写方向无法对称（写回要反算，反算错 = 控制动作错）。

    ⚠️ 例外（**协议内在语义**，不是用户配置）：S7 的 `StringKind` 等 协议规定的编码转换在驱动层完成 —— 那是"把线上字节变回协议定义的数值"，与"用户想让读数乘 0.1"是两件事，不受本契约限制。

    [!!]【2026-11-19 订正】本仓存在**两种**驱动模型，原文只描述了第一种：

    驱动层解码模型（多数协议）——返回 IEEE754 字节： MBus / DLMS / HART-IP 及 PLC 系驱动都先解析出 `double`/`float`， 再经 `EncodeWireBytes` 按本类 `EndianConverter` 编成字节返回 （见 `MbusDriver.cs:197-208`（`ParseResponse` → `EncodeWireBytes`））⇒ 调用方按 `DataTypeCode` 配 `float`/`double` 即得**工程值**，属协议内在语义，不受本契约限制 ✓

    字节透明模型（仅 DLT645 / CJT188）：这两个驱动**不解码** （`Cjt188Driver` 文件头明确「不编解 BCD、不理解数据语义」； `Dlt645Driver` 只做 −0x33 与剥 DI）⇒ 本属性给的是原始字节 （低字节在前、BCD 编码）⇒ 调用方须按协议表解码： 反序 → BCD→整数 → ÷10^digit，通用原语见 ZL.IotAbstraction.Abstractions.MeterBcd。

    [!] 原文此处笼统写「CJT188 的 BCD 解码、DLT645 的 BCD…在驱动层完成」， 对驱动层解码模型成立、对字节透明模型 不成立（2026-11-19 跨仓实测发现，`ZL.IotDetector/docs/110`）。 为避免误读，两个字节透明驱动的类型化读/位读已改为**响亮失败** （`SupportsTypedScalarReads = false` + `ShouldDenyBitRead`），而不是静默返错值。
