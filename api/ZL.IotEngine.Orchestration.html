    DeviceBase

    简化版设备基类 —— 工控 PLC 数据采集的「轻量驱动骨架」。

    与 DevicePro（高级版，含 QoS 写入队列、ConnectionStateManager）不同， 本类面向中小型采集场景：直接同步读写 PLC 寄存器，不使用写入队列和连接状态机。

    核心职责： 1. 连接生命周期管理（初次连接 + 断线指数退避重连） 2. 多频率后台扫描引擎（按标签组 ScanRate 分波次轮询 PLC） 3. 心跳写入（独立锁，不阻塞业务读取） 4. 按数据类型分发同步/异步读写 5. 资源释放（Dispose 模式）

    继承链：DeviceBase → DeviceRoot（标签管理/计划构建/事件发布）→ object 实现接口：IDeviceDriver（驱动契约）、IPlcDriver（PLC 读写契约）、IDisposable

    DeviceManager

    设备实例管理器（单例模式）：确保每个物理 PLC 在应用程序中只有一个对应的驱动实例。

    工控背景：在工业采集系统中，同一个 PLC 如果被多个采集模块重复创建连接， 会导致端口冲突、数据不一致、PLC 连接数耗尽等严重问题。 本管理器通过 ConcurrentDictionary 实现线程安全的单例管理， 保证整个应用生命周期内，同一 DeviceId 只对应一个驱动实例。

    DevicePro

    PLC 设备驱动的高级基类（全功能版）。

    在工控采集场景中，DevicePro 承担以下核心职责： 1. 连接生命周期管理 —— 自动重连、存活探测、连接状态机； 2. 周期性批量读取 —— 由**基类 `DeviceBase`/`DeviceRoot` 的波次循环**完成 （`BuildPlan` 建块 ＋ `ExecutePlanByRate` 多速率调度），减少网络往返； ⚠️【2026-11-11 订正】原写「通过 `BatchEngine` 合并」—— **该类已于 `24bfaaba` 删除** （它是"从未接线的第二采集引擎"，零引用），采集引擎已收敛为 `DeviceRoot` 单一实现 ✗→✓； 3. QoS 分级写入 —— 安全写（联锁/急停）绝对优先，普通写可合并去重； 4. 心跳保活 —— 定期向 PLC 写入翻转位，让对端判定上位机是否存活。

    与 DeviceBase 的区别：DevicePro 内置写队列和连接状态机， 适用于需要"安全写入优先 + 普通写入去重"的关键控制场景（如配方下发、报警复位）； DeviceBase 则适合只读采集或对延迟不敏感的辅助回路。

    DeviceRoot

    设备采集根类 —— 整个 PlcBase 库的「采集引擎核心」。

    在工控 SCADA/MES 集成场景中，本类承担以下关键职责： 1. 标签管理：从配置文件或内存字典加载 PLC 点位标签（Tag），按用途分为监控标签(M)、心跳标签(HB)、就绪标签(RO)。 2. 采集计划构建：将分散的标签地址合并为连续的「读取块」(PlcReadBlock)，减少 PLC 通讯往返次数，提升吞吐量。 3. 批量读取调度：按扫描频率(ScanRate)分组执行读取计划，支持自适应间隔调整（快设备快采、慢设备慢采）。 4. 质量管理与坏点隔离：连续读取失败的通讯块会被拆解为单点探测，坏点地址自动隔离，定时自愈。 5. 变更检测与事件发布：对比本地缓存，仅当值变化超过死区(Deadband)时才触发 DataChange 事件，降低下游压力。

    子类（如 DevicePro、DeviceBase）通过实现抽象方法来适配具体的 PLC 协议（西门子 S7、Modbus TCP、汇川等）。

    DriverFactory

    统一驱动工厂 —— 对外的唯一推荐入口。

    路由策略：

    • 默认走 Native：无前缀（如 "siemens-s7"）或带 "native-" 前缀均走自研驱动。 Native 是零商业依赖的默认选择。
    • 显式走 HSL：Protocol 以 "hsl-" 开头，或传入 DriverBackend.Hsl。 仅在需要 HSL 独有能力时使用（需先调 XInit.EnsureInitialized()）。

    典型用法：

    // 最简：走 Native（推荐，无前缀即 Native）
config.SetParam("Protocol", "siemens-s7");
var driver = DriverFactory.Create(config);

// 订阅标签变化事件（必须通过 ITriggerableDriver 接口，不要通过具体类型判断）
// ✓ 正确：通过接口，新增驱动类型自动生效，无遗漏
if (driver is ITriggerableDriver triggerable)
    triggerable.TriggerDataChanged += (id, value, tag) => { ... };

// ✗ 错误：通过具体类型 switch，将来新增驱动时静默丢失事件
// if (driver is HslUnifiedDriver hsl)  hsl.TriggerDataChanged += ...
// if (driver is NativeUnifiedDriver nat) nat.TriggerDataChanged += ...

// 显式走 HSL（唯一走 HSL 的方式）
config.SetParam("Protocol", "hsl-siemens-s7");
var driver = DriverFactory.Create(config);

// 后续用法与 IPlcDriver 一致，无需感知底层
await driver.ConnectAsync(ct);
driver.DataCollected += record => ...;

    IPlcDeviceExtensions

    IPlcDevice 的泛型扩展方法集合——简化标量和数组的读写操作。

    设计意图：在不修改 IPlcDevice 接口的前提下，提供泛型 Read/Write 的便捷 API。 所有方法基于 ReadBytesAsync/WriteBytesAsync + IEndianConverter 实现， 零破坏性，不影响任何现有驱动实现。

    ManagedDeviceBase

    托管设备基类 —— 自动管理 Driver 和设备生命周期。

    继承 DeviceBase，自动完成以下工作： 1. 调用 Create(DeviceConfig) 创建驱动（Native/HSL 自动路由） 2. 订阅驱动的 TriggerDataChanged 事件 3. 将事件转发到业务钩子 OnManagedTriggerDataChange(string, object, TagItem)

    业务端只需继承此类，实现构造函数，重写 OnManagedTriggerDataChange(string, object, TagItem) 即可。 无需关心 Driver 创建、连接管理、事件订阅等基础设施代码。

    🔴 注意：OnTriggerDataChange(string, object, TagItem) 在本类是 sealed 的， **不供业务重写**（它只负责把两条上游链路汇聚到业务钩子）。 历史上该注释曾写"重写 OnTriggerDataChange"，与实际签名矛盾 ⇒ 2026-10-30 更正。

    OverrunMonitor

    周期 overrun 监控器（docs/653 D2）。每台设备（每个扫描桶）一个实例。

    为什么需要：CustomPeriodicTimer 的语义是"从**绝对时间点**起算" —— 本轮耗时 > scanRate 时**下一 tick 立即返回**（不等待） ⇒ **背靠背满负荷**（是"打满"，不是"降频"）。现场只能看到"数据在动但周期不准"， **没有任何指标**说明"你要的 100ms 做不到" ✗

    为什么不放在 DeviceBase 里：那个文件已**超行数基线** （`㊲` 门禁「只减不增」）⇒ 按门禁推荐①「按职责切」抽出来 ✓
