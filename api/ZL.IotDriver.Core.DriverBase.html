    Class DriverBase

    驱动基类的公共父类：只承载与传输方式无关的能力。

    【分层】DriverBase → NativeDriverBase（TCP 套接字）/ SerialDriverBase（串口） ⇒ 传输是**变化点**，放在子类；协议无关逻辑只写一份 [OK]

    【为什么本类**不**实现 IPlcDevice】若在这里实现接口，就必须一次搬完所有接口成员 （含传输相关的 `ReadBytesCore` 等）⇒ 变成"大爆炸重写" [X] 故本类只声明它自己用到的抽象成员，由两个子类各自履行接口 [OK]

    TypedAccess

    本协议是否支持类型化读（ReadInt16 / ReadFloat / ReadString 等）。

    覆写判据（不是看协议名字，是看行为）：若本驱动的值区**不能**直接按 `short`/`int`/`float`/`string` 解释 —— 即需要 BCD 解码、字节反序、或按点位小数位 缩放才能得到协议定义的数值 —— 就**必须**覆写为 `false`。 典型：DLT645、CJT188（两者都是"值区 = BCD + 低字节在前 + 每 DI 小数位不同"）。 反之，在驱动内部已解析成 `double`/`float` 并按 `EndianConverter` 编成字节的驱动 （如 MBus / DLMS / HART-IP）保持默认 `true` 即可。

    [!!] 为什么必须拦：以 DLT645 的 A 相电压（DI `02010100`）为例， 线上值字节 `11 23`（`-0x33` 后）⇒ `ReadUInt16` 按大端得 **4387**， 真值 **231.1 V**（差约 19 倍），而**量纲看起来仍像电压** ⇒ 现场极难发现。 **静默错值比报错危险得多** ⇒ 这类协议必须**响亮失败**。

    正确读法：`ReadBytes` 取原始字节 ⇒ 按本协议规定解码 （DLT645/CJT188 为：**反序 → BCD→整数 → ÷10^digit**）。 通用 BCD 原语见 `ZL.IotAbstraction.Abstractions.MeterBcd`； CJT188 另有专用值层 `ZL.IotDriver.CJT188.Cjt188Value`（含单位表/特殊值/时间）。

    [!] 与 `ReadBytes` 的边界：本标志**只拦类型化读**（`ReadInt16`/`ReadFloat`/ `ReadString` 等）；`ReadBytes` **不受**本标志影响 —— 它是取原始字节的正当出口。

    TypedReadUnsupportedHint

    本协议不支持类型化读时给出的提示（消息必须自足：讲清怎么改用）。

    [!] 刻意做成**可覆写**：默认文案只说"交付原始字节、按协议规定解码"， 不声称具体编码（如 BCD）—— 因为"哪个协议用什么编码"是协议特有的， 通用基类替所有协议断言编码会**说谎**。设了 `TypedAccess = ByteTransparent` 的驱动 应覆写本属性，写清**本协议**的实际编码与解码方法。

    GetEndianConverter()

    取本驱动的字节序转换器（抽象，由两个基类各自返回自己的 EndianConverter）。

    [!] 为什么用方法而不是抽象属性：两个基类对该成员的声明**不同** —— NativeDriverBase 是 public virtual IEndianConverter EndianConverter { get; protected set; }， SerialDriverBase 是 public abstract IEndianConverter EndianConverter { get; }。 若在 DriverBase 声明 abstract ... { get; }，Native 带 setter 的实现**无法 override**（CS0546）[X] ⇒ 改用方法取用，两边各自 `=> EndianConverter`，语义完全等价 [OK]

    ValidateWriteArray<T>(T[])

    【2026-10-20 新增 [OK]：读长度单位的显式契约 [X]→[OK]】。

    【为什么需要它 [X]】基类长度守卫要求「驱动返回的字节数必须等于请求的 `length`」[OK]， 但 **`length` 的单位是「协议单位」而不是「字节」** [X] —— **Modbus 系**里 `ReadBytes(addr, n)` 的 `n` 是**寄存器数** [OK]（每寄存器 2 字节 [OK]） ⇒ 驱动**合法地**返回 `n × 2` 字节 [X]。

    【曾经的错误 [X]→[OK]（我引入的回归 [OK]）】`9acac3d` 把守卫从「不少于」改成「**恰好等于**」[X]， 本意是堵住"给多了也静默错值"[X]（单值驱动 `ReadInt16` 取 float 高字节 [X]）—— 但**没有区分单位** [X] ⇒ `ModbusRtuOverTcp` 的 `ReadInt16` 直接被判失败 [X][OK]。 [!] **门禁一直是绿的** [X] —— 因为**没有门禁测试覆盖 Modbus 读** [X]； 是**交叉测试**（`SelfConsistency` [OK]，不在 CI [X]）把它抓出来的 [OK][OK] （`docs/drivers/ISSUES.md` 之外的**我自己的问题** [OK]）。

    【本方法怎么根治 [OK]】把「单位」变成**显式声明的契约** [OK]： 基类默认「`length` 就是字节数」[OK]；**若某协议单位不是字节，子类覆写本方法** [OK]。 ⇒ 守卫仍严格 [OK]，但**比的是正确的期望值** [OK] ⇒ 既不再误伤 Modbus [X]， [!] 【2026-10-21 更正 [X]→[OK]】原文写「Modbus 系覆写为 `length × 2`」[X] —— **实测全仓零覆写** [OK][OK]。 原因：Modbus 系**已在 `ReadBytesInternal` 内截断到 `length`**（`ModbusTcpDriver.ReadBytesInternal` 内的 `new byte[length]` 截断；[!!] 行号易漂移 ⇒ **以符号为准**） ⇒ 交给基类时**就是 `length` 字节** ⇒ **无需覆写** [OK]。本方法目前无任何子类覆写 [OK]， 留着是为了「新增协议若单位不同」时**有唯一收口点** [OK]。 也保留"给多/给少都算违约"的检查 [OK][OK]。

    [!] 新增协议若单位不是字节 [OK]，**必须**覆写本方法 [OK] —— 否则会被守卫误判 [X]。

    WriteTypedBytesAsync(string, byte[])

    类型化写的边界（易混，必须写清）—— 是否被拦由 TypedAccess 统一决定：

    • 被拦：`Write(address, 数值/bool/string)` 与 `WriteAsync(address, 数值/bool/string/数值[]/bool[])` —— 这些是"由 SDK 按 `EndianConverter` 或**固定 ASCII** 编码"的便利重载。
    • 不拦：`Write(address, byte[])` / `WriteAsync(address, byte[])` —— 调用方自己编好字节的正当出口。
    • 不拦：`WriteString(address, value, kind, maxLength, encoding)` —— 它要求调用方**显式**给出 `StringKind` + `maxLength` + `encoding`， 且最终走 `Write(address, byte[])`；属"调用方自己编码"。 （与 `Write(address, string)` 不同：后者是**固定 ASCII** 的便利重载，被拦。）
    • 被拦（间接）：`Write(address, object)` —— 经 `DeviceWriteDispatch` 按运行时类型分派到上面的 typed 重载，因此同样受 TypedAccess 约束。

    [!!] 为什么写侧比读侧危险：读错只是显示错；写错会改变表内状态 （如把 2311 按大端写成 09 07，而表要 BCD 低字节在前的 11 23）⇒ 表可能把该值当成另一个数、或直接拒绝，且现场很难回溯是哪一次写坏的。
