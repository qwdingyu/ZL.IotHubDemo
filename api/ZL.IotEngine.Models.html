    Namespace ZL.IotEngine.Models

    Classes

    IoPerformanceMonitor

    IO 性能监控器——集中管理所有 IO 操作的分类指标。

    在工控采集系统中，PLC 通讯可能涉及多种操作类型（读取、写入、心跳、批量读等）， 每种操作的性能表现可能差异很大。IoPerformanceMonitor 按操作名称分类统计， 便于运维人员快速定位瓶颈： - 读取平均耗时 50ms 但写入平均耗时 500ms → 可能是写入帧构造过慢； - 心跳成功率 100% 但批量读成功率仅 80% → 可能是批量帧过大导致超时。

    使用 System.Collections.Concurrent.ConcurrentDictionary<TKey, TValue> 保证线程安全， 多个采集线程可以同时向不同操作名写入指标而无需加锁。

    NormalWriteRequest

    普通写入请求——可被合并去重的低优先级写入操作。

    在工控场景中，HMI 界面上的滑块或输入框可能频繁触发写入请求（如用户拖动滑块）， 但 PLC 通讯带宽有限，不能每次都实际发送。NormalWriteRequest 被放入写入队列后， 如果同一地址有新的请求到来，旧请求可以被合并/丢弃（取最新值）， 从而减轻 PLC 通讯压力，避免"写入风暴"。

    通过 System.Threading.Tasks.TaskCompletionSource<TResult> 将异步结果返回给调用方， 调用方 await 即可获知写入是否成功。

    SafetyWriteRequest

    安全写入请求——不可合并、必须保证执行的高优先级写入操作。

    与 NormalWriteRequest 的核心区别： - NormalWriteRequest 可被合并去重（同一地址只保留最新值），适用于 HMI 手动操作； - SafetyWriteRequest 走**高优先级安全写队列**（可插队普通写），适用于安全联锁、急停复位等关键操作。

    ⚠️ **但"不可丢弃"目前不成立（2026-10-31 实测）**：安全写 Channel 容量 200、 `FullMode = DropOldest` ⇒ **队列满时会静默丢弃最旧的一条**， 且**没有告警**（`DevicePro` 注释声称有告警，代码中不存在）。 调用方不会挂死（有 `SafetyWriteTimeout`，默认 2000ms 兜底），但会收到 「写入超时或被取消」——**真实原因可能是"队列满被丢弃"** ✗

    支持"操作序列"（Sequence）：在工控场景中，某些操作需要按严格顺序执行 （如先关闭阀门 → 再停止泵 → 最后打开排放阀）， ⚠️ **排序尚未实现（2026-10-31 实测，勿再误传）**：`SequenceId` / `SequenceOrder` 目前**只被赋值、从未被读取**；安全写 Channel 是 FIFO， 执行顺序**只取决于入队先后**，与 `SequenceOrder` 无关 ✗

    ⇒ 需要"先关阀 → 再停泵 → 最后开排放阀"这类**严格顺序**时， **调用方必须串行入队并逐条等待结果**，不能靠并发入队 + `SequenceOrder` 排序。

    复核命令（阳性对照：赋值应有 2 处；读取应为 0）： grep -rn "SequenceOrder =\|SequenceId =" ZL.IotEngine/ tests/ grep -rnE "\.SequenceOrder|\.SequenceId" ZL.IotEngine/ tests/ | grep -v "SequenceOrder =\|SequenceId ="

    内置重试机制：通过 executionAttempts 原子计数器跟踪执行次数， 最多重试 3 次（工控通讯偶发超时时需要自动重试以保证可靠性）。

    TagValue

    工业级数据载体——每个 PLC 点位的"值 + 质量 + 时间戳"三元组。

    这是整个采集系统中最基础的数据单元，类似于 OPC 中的 DataItem： - Value：从 PLC 读到的原始值（可能是 bool/int/float/string 等）； - Quality：数据质量码，标识该值的可信程度； - Timestamp：采集时刻的时间戳，用于趋势图、数据回溯等场景。

    【不可变性保证】 此类为不可变（immutable）——所有属性通过构造函数一次性设置，之后不可修改。 多线程环境下可安全共享，无需额外同步。更新值时创建新实例（copy-with-update）， 配合 ConcurrentDictionary.TryUpdate 的 CAS 语义实现无锁数据流。

    对标方案： - OPC UA .NET Stack: DataValue (Value, StatusCode, SourceTimestamp, ServerTimestamp) — 全 readonly - Beckhoff TwinCAT: PlcTag — immutable snapshot 模式 - Eclipse Milo: DataValue — 不可变 + 工厂方法

    TagValueChange

    点位值变化事件载体——当某个 Tag 的值发生变化时，通过事件总线分发给订阅者。

    在工控场景中，"变化推送"（Change-of-State / CoV）是减少数据流量的核心策略： 只有当值真正发生变化时才通知上层（MES/SCADA/HMI），避免每个采集周期都推送大量未变化的数据。

    与 TagValue 的区别：TagValue 是"当前值快照"， TagValueChange 是"变化事件"，携带 TagId 和 TagItem 元数据， 便于订阅者直接定位到具体点位定义。

    Enums

    SafetyLevel

    PLC 写入操作的安全等级分级——数值越小优先级越高。

    在工控场景中，向 PLC 写入数据必须按安全等级分级管控： - 紧急停止类操作（如复位安全标志）必须立即执行，不可排队或合并； - 过程控制类操作（如写入配方参数）需要保证顺序和完整性； - 普通操作（如 HMI 手动设值）可以合并去重以减轻 PLC 通讯压力。

    数值设计采用"越小越优先"的方式，便于在优先级队列中用最小堆排序。

    TagQuality

    数据质量代码，对标 OPC DA/UA 标准中的 Quality 字段。

    在工控采集中，每个从 PLC 读取的点位都需要附带质量码， 上位系统（MES/SCADA/HMI）根据质量码判断数据是否可信： - Good(0xC0)：数据来自 PLC 实时读取，可放心使用； - Uncertain(0x40)：通讯短暂中断，保留最后一次有效值（"陈旧值"），上位可酌情使用或报警； - Bad(0x00)：通讯完全失败或地址配置错误，数据不可信； - Initializing(0x01)：设备尚未完成首次采集，值为默认值。

    质量码数值设计参考 OPC 规范的高/低两位编码方式， 便于通过位运算快速判断大类（Good≥0xC0, Uncertain≥0x40, Bad=0x00）。
