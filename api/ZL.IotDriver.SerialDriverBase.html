    CheckFixedReadWidth(int, int, string)

    【单值仪表类驱动的长度契约守卫】docs/436 §十四

    部分串口协议（Mewtocol / DLMS / M-Bus）**只有"读一个值"的语义**， 其响应宽度由协议固定（float=4 字节 / double=8 字节），**不存在"读 N 字节"的概念** [X]。 这类驱动的 ReadBytesCore 会忽略 length 而恒返回固有宽度：

    • 宽度**不匹配**时，基类长度守卫会以"返回 X 字节，与请求的 Y 字节不符"报错 [OK]， 但现场看不出"该怎么办" [X] ⇒ 本方法把它换成**可操作的提示** [OK]；
    • 宽度**匹配**时返回 null，行为与不调用本方法**完全一致** [OK]（零行为变更）。

    [!] 语义澄清（避免误判为"缺陷"）：length 仍按契约表示**字节数** [OK]； 只是这类协议**只支持一个固定宽度** ⇒ 点表必须把 DataTypeCode 配成对应类型 （如 M-Bus 必须配 double；Mewtocol/DLMS 必须配 float）。

    ConnectClose()

    关闭连接（幂等：未连接时也应返回成功）。

    [!] 实现方**必须**释放底层 socket/串口，否则端口泄漏会拖垮后续测试与重连 [OK]

    [!!] **本方法就是本接口的资源释放契约** —— 不要再给 IPlcDevice 加 IDisposable / IAsyncDisposable。

    【为什么（三条实测依据，勿凭印象推翻）】

    1. **框架已调用它**：`DeviceBase.Dispose()`（`ZL.IotEngine/Orchestration/DeviceBase.cs`） 方法体内有 `Device?.ConnectClose();` ⇒ 释放闭环是 `Dispose()` → `ConnectClose()` → 底层 `Dispose()/Close()`，**不需要第二个释放入口**。

      [!!]【2026-11-13 补充实测】该闭环只覆盖 **`Dispose`**；**"重连替换 `Device`"** 是另一条路径， 曾**不关旧实例**（`DeviceRoot.Device` 是 public 字段，赋值即静默丢弃）⇒ 每次重连滞留 1 个 TCP 句柄直到 GC（实测 lsof：+1/次，强制 GC 归零）。 已于 2026-11-13 在 `NativeUnifiedDriver.Connect()` / `HslUnifiedDriver.Connect()` 补 `ConnectClose()`； 完整证据。

    2. **`IAsyncDisposable` 需要额外依赖，且收益为零**： `netstandard2.0` / `net48` 的 BCL **不含** `System.IAsyncDisposable`， 要用必须给本包新增 `Microsoft.Bcl.AsyncInterfaces` 依赖 （旁证：`ZL.IotHub.Bridges` 因 SignalR 传递**已有**该包，其 `SignalRPlcBridgeSink` 在 net48 / netstandard2.0 **实测可编译** ⇒ 不是"不可能"，而是"要付一个依赖的代价"）。 但见下条：底层无异步释放 ⇒ **不值得付**。

      [X]【2026-11-13 订正】本节原写「在本仓目标框架上**不可用**」并附"独立探针报 4 个错误"—— 该探针工程**没有** `Microsoft.Bcl.AsyncInterfaces`，测的是"裸环境"而非"本仓"[X] 结论（不加 `IAsyncDisposable`）不变，**论据**已改为"依赖代价 + 零收益" [OK]

    3. **底层资源本身没有异步释放**：实测 `TcpClient`、`NModbus.IModbusMaster`(3.0.83) 的 `IAsyncDisposable` 均为 `False`；`S7.Net.Plc`、`SerialPort` 只有同步 `Close()`/`Dispose(bool)` ⇒ 即使加 `DisposeAsync()`，内部也只能调同步释放，**零收益**。

    【若给接口加 `IDisposable` 的代价（为什么不做）】 `ZL.IotAbstraction` 是**已发布 NuGet 包**（2.3.0）⇒ 主版本破坏性变更； 跨仓消费者（UseThink.Iot / tmom）升级即断； 且形成 `ConnectClose()` 与 `Dispose()` **两条释放路径** ⇒ 需额外防重复释放。

    [X]【2026-11-13 订正】原文写「全部实现类**立即编译失败**（本仓实测 54 个：生产 16 ＋ 测试 38）」—— **计数口径错**：54 是"出现 `IPlcDevice` 的类型数"，不是"会 CS0535 的类数"。 实测：生产侧**直接声明** `: IPlcDevice` 的类共 **15** 个，其中 **11** 个**已实现 `IDisposable`** （`NativeDriverBase`/`SiemensS7Driver`/`MitsubishiMcDriver`/`BeckhoffAdsNet`…）⇒ 不会因接口新增而失败； 真正会失败的只有 `NModbusDeviceAdapter`/`S7PlusDeviceAdapter`/`HslToDeviceAdapter` ＋ 测试侧直接声明且无 `Dispose` 的约 6 个文件（继承 `StubPlcDeviceBase` 等的子类**不受影响**）。 ⇒ **真正代价是 SemVer 破坏 + 跨仓断链**（上面两条），不是"54 个编译失败" [OK]

    【回归防护】门禁 `scripts/audit/check_connect_close_release.py`（㊸） 静态检查每个 `ConnectClose()` 方法体**必须**含释放调用 （直接 `.Dispose()/.Close()/= null`，或间接调用名字含 `Close/Dispose/Release/Cleanup/Shutdown/Teardown/Destroy` 的辅助方法）。

    EncodeWireBytes(float)

    【2026-10-20 新增 [OK]：*Core 交出「线上字节」的唯一出口 [X]→[OK]】。

    为什么必须有它 [X]（`docs/drivers/ISSUES.md` ISSUE-002 [OK]）： 本基类契约是「**`ReadBytesCore` 交出线上原始字节 [OK]，字节序由基类按 `EndianConverter` 统一解释**」[OK]。 但有 **5 个**串口驱动（`Dlms` / `HartIp` / `PanasonicMewtocol` / `MBus` / `MelsecFx` [X]） 在 `*Core` 里自己写了 BitConverter.GetBytes(值) + Array.Reverse [X] —— 那是**主机序字节** [X]，不是线上字节 [X][OK]。

    为什么它是隐患 [X]：三者凑成「**负负得正**」[X] —— 驱动先把值转成**大端** [OK]（`Array.Reverse` 恰好抵消主机小端 [OK]）， 基类再按声明（也常是 `BigEndian` [OK]）解释一次 [OK] ⇒ **结果碰巧正确** [OK]。 只要**任一端改了声明** [X]（或漏了那句 `Reverse` [X]）⇒ **双重错** [X][OK] —— `MBus` 是活证据 [X]：它**漏了** `Array.Reverse` [OK] ⇒ 写 `1.0` 读出来 `3.03865E-319` [X]（2026-10-20 实测 [OK]）。

    本出口如何根治 [OK]：它**用同一个 `EndianConverter`**（基类解码用的那个 [OK]）编码 [OK] ⇒ **编码与解码结构上不可能分叉** [OK][OK]；且对原本「碰巧正确」的驱动**字节完全等价** [OK] （已实测 [OK]：`float 3.14159f` 两条路径都得到 {0x40,0x49,0x0F,0xD0} [OK]）⇒ **零行为变更** [OK]。

    [!] 它只解决「**驱动不要自己管字节序**」[X] 这一件事 [OK]； 「真的去读整段线上字节」（多寄存器读 [OK]）是另一层工作 [OK]，不在本出口范围 [X]。

    TryEnsurePortOpen<T>(out DeviceResult<T>)

    在持 _lock 之前确保串口已打开；失败时返回 false 并给出失败结果。

    ── 2026-09-20 修复（自死锁）──────────────────────────────── 【缺陷】EnsurePortOpen() 内部可能调用 ConnectServer()， 而 ConnectServer 自身会取 _lock。部分串口驱动把 EnsurePortOpen() 写在 _lock.Wait() 之后（即已持锁）， System.Threading.SemaphoreSlim 不可重入 → 该调用将永久阻塞。

    【触发窗口】IsReadyToOperate 通过（此刻 IsConnected==true）之后、 _lock.Wait() 之前，若另一线程执行 Dispose() → _disposed=true + ConnectClose() 关闭串口，则本线程取锁后 IsConnected 变为 false，EnsurePortOpen() 遂走 ConnectServer → 重入 _lock → 死锁。 DeviceBase.DisposeAsync 在 3 秒超时后不等待后台循环即继续释放， 使该窗口在正常停机流程中即可命中。

    【为何不直接把 EnsurePortOpen() 移出锁区】它会抛 InvalidOperationException；移出 try 后异常将外泄给调用方， 破坏 DeviceResult 的"不抛异常、以 Fail 表达失败"契约 （调用方如 DeviceBase.ReadValue 并不捕获异常）。 故本方法把异常转为失败结果，同时把调用点移出锁区。
