    Class DeviceManager

    设备实例管理器（单例模式）：确保每个物理 PLC 在应用程序中只有一个对应的驱动实例。

    工控背景：在工业采集系统中，同一个 PLC 如果被多个采集模块重复创建连接， 会导致端口冲突、数据不一致、PLC 连接数耗尽等严重问题。 本管理器通过 ConcurrentDictionary 实现线程安全的单例管理， 保证整个应用生命周期内，同一 DeviceId 只对应一个驱动实例。

    ReadByDeviceIdAsync<T>(string, string, CancellationToken)

    异步读取指定设备的标签。

    2026-09-20 修复（静默成功缺陷）：DeviceBase 分支原先 无条件返回 IsSuccess = true —— 即使标签不存在 / 无效 / 读取失败（DeviceBase.Read<T> 以 default(T) 表达失败）， 也会报"成功"。调用方拿到的 0 / null 无法与"真实读到 0"区分， 属本领域最危险的**静默错误**；且与本方法 DevicePro 分支 （ReadTagValueAsync 对缺失标签明确返回 IsSuccess=false）语义不一致。

    现改为：读前先校验标签存在且有效（判据与 Read<T>(string) 内部一致）， 任一不满足即返回失败结果；校验通过后再取值。既保持 Read 不抛异常的既有语义， 又让 IsSuccess 真实反映"标签可读"。

    【已知边界】DeviceBase 无异步读通路（其读是同步的）， 故本分支仍在调用线程同步执行 Read<T> —— 属既有实现约束， 非本次修复范围（改为真异步需为其新增异步读 API，属独立变更）。

    Register<T>(DeviceConfig, T)

    将【已构造好的】设备实例注册到管理器（按 DeviceId 单例管理）。

    为什么需要：GetDevice<T>(DeviceConfig) 是唯一历史注入路径，但它用 Activator 反射构造 调用方指定类型，无法接纳"外部已经建好的实例"。 编排器改造后，底层统一驱动经 Create(DeviceConfig) 创建（路由/门禁/计数单点收敛，docs/148 A1），必须再把产物注册进来， 否则 ReadByDeviceId / WriteByDeviceId / GetDeviceRootById 等按 ID 寻址的 API 对编排设备全部不可达 —— 上层（如 Gear 的 DeviceManagerTagWriter） 的写入链会整条断裂。

    单例语义与 GetDevice<T>(DeviceConfig) 对齐：同一 DeviceId 只保留 【首个】实例（GetOrAdd 原子判定），后续注册返回已在册实例、不覆盖 —— 防止同一物理 PLC 双连接双计数。未中标的实例其生命周期由调用方自理 （典型做法：调用方负责释放，归还授权名额）。
