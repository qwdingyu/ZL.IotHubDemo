    SendCommandThenConfirm(byte[], byte)

    ⭐⭐⭐ PPI 两阶段交互（这是 PPI 最容易被漏掉的机制 ✗）。

    🔴 **初版我只有"发一帧收一帧"，是错的** ✗ —— 由 `PpiHslServerCrossTests` 端到端对拍抓出（收到单字节 `0xE5` 就被当作完整响应 ⇒ `CheckResponse` 报"响应过短" ⇒ **永远读不到数据**）✗✗

    正确流程（HSL `SiemensPPIHelper.cs:444-456` / `:508-521` 原文）： 

    ① 发命令帧                      →  收【单字节 0xE5】（仅表示"已收到"）
② 发 BuildExecuteConfirm 帧      →  收【真正的数据/写结果】

    阶段 ① 收到的必须是单字节 0xE5；否则 HSL 报 "PLC Receive Check Failed"（:452）⇒ 我方同样明确失败 ✓

    PPI 无 seq 字段 ⇒ **不做重试**（重试会导致重复写入风险 ✗）；失败即返回。

    Write(string, bool)

    位写（标量） —— 2026-11-16 永久修复（台账 BZ-PPI ①）。

    【为什么必须覆写：原实现把 1 位写成 8 位】基类 `Write(string,bool)` （`NativeDriverBase.cs`）把 bool 转成 **1 字节** 后调 `WriteBytesCore` ⇒ 走 `PpiFrame.BuildWriteBytes` ⇒ 帧内 `access[22]=2`（字节）、`len[24..25]=1 字节`、 `bits[33..34]=8` ⇒ PLC 实际写 **8 位**（`AddressStart` 单位是**位**）⇒ `Write("V100.3", true)` 会连 **V100.4~V100.7 与 V100.0~V100.2 一起被改**（误伤 7 个邻居）[X]。

    【权威依据（HSL 13.0.3 原件，逐字）】 · `DeviceCommunication.cs`：`Write(string address, bool value) => Write(address, new bool[1] { value });` · `SiemensPPI.cs:67-70`：`Write(string address, bool[] value) => SiemensPPIHelper.Write(this, address, value, Station, communicationLock);` ⇒ **所有 bool 写（含无点号地址）都是"位写"**，与"地址是否含点号"无关。

    【行为变更（须写发布说明）】`Write("V100", true)` 此前写"字节 V100 = 0x01"（8 位）， 现在写"位 V100.0"（1 位、不动邻居）—— 与 HSL 语义对齐。
