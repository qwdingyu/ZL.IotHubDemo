    AddDeviceAsync(DeviceConfig, CancellationToken)

    运行时新增一台设备（docs/653 D13，2026-11-17）：创建 → 启动。

    为什么要它：现场调试常需要"临时加一台设备试试"， 而原 API 只有构造期批量加载（`MultiDeviceOrchestrator` 只从 fleet 配置建）⇒ 加一台必须重启整个宿主 ✗

    幂等：复用 ZL.IotEngine.Orchestration.MultiDeviceOrchestrator.CreateDevice(ZL.IotAbstraction.Tag.DeviceConfig) —— 同 `DeviceId` 已存在时**复用**实例 （不重复创建、不二次计数、**不**记入 `_ownedDeviceIds`）⇒ 之后 `RemoveDeviceAsync` 也**不会**释放它（所有权在原持有者）✓

    失败语义：连接/建计划失败时**返回** `IsSuccess=false` 的 DeviceStartResult（**不抛**），且设备**仍在** `_devices` 里 —— 调用方可重试或显式 `RemoveDeviceAsync` 摘掉 ✓

    GetDeviceIds()

    获取所有设备 ID。

    🔴 **【2026-11-09 补充文档（docs/629 / A-238）】返回顺序**不保证**** ✗ —— 底层是 System.Collections.Concurrent.ConcurrentDictionary<TKey, TValue>， 其**枚举顺序是未定义的**（不保证插入序）⚠️。 实测（`docs/629`）：传入 `[DEV-A, DEV-B]` ⇒ 本方法返回 **`[DEV-B, DEV-A]`**（相反）✗

    ⇒ **不要**写 `GetDeviceIds()[0]` 并假设它是"配置里的第一台" ✗ （会让"编号 ↔ 设备"的对应关系不稳定 ⇒ 现场按编号排障时**指错设备**）⚠️

    ✅ **需要稳定顺序**（与配置传入顺序一致）请用 GetDeviceIdsInConfigOrder() ✓； 或者调用方自己 `OrderBy`（若只是要一个确定的序）✓

    GetDeviceIdsInConfigOrder()

    【2026-11-09 新增，docs/629 / A-238】按设备注册的首次出现顺序返回设备 ID —— 即"与配置传入顺序一致"，可比 GetDeviceIds() 的未定义顺序安全使用 ✓

    **与 GetDeviceIds() 的差异**：本方法只保证**顺序**； 两者返回的**集合内容相同**（都来自当前在册设备）✓ —— 已释放的设备两者都不会返回 ✓

    **实现**：用一条独立的顺序表（`_deviceIdOrder`）记录首次注册顺序， 再按它过滤当前在册集合 ⇒ 既稳定、又不会返回已摘除的设备 ✓

    RemoveDeviceAsync(string, CancellationToken)

    运行时移除一台设备（docs/653 D13，2026-11-17）：从本编排器摘除 → 仅自有则释放。

    与 StopAsync(CancellationToken) 的区别：`StopAsync` 只停**全部**且保留在 `_devices` 里； 本方法摘掉**单台**并使其不再出现在 `GetHealthStatus`/`GetDeviceIds`/`DeviceCount` 中 ✓

    所有权：复用 ReleaseOwnedDevice(string, DeviceRoot) —— 它用**原子占位**保证"恰好释放一次"，且对**复用设备**返回 `false` （只从本编排器摘除，**不动**其生命周期与 `DeviceManager` 注册）✓

    返回值：不在本编排器里 ⇒ `IsSuccess=false`（**幂等**，不抛）； 摘除成功 ⇒ `IsSuccess=true`，`Message` 说明是否真正释放了设备 ✓
