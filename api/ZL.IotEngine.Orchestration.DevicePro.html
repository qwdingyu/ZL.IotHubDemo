    Class DevicePro

    PLC 设备驱动的高级基类（全功能版）。

    在工控采集场景中，DevicePro 承担以下核心职责： 1. 连接生命周期管理 —— 自动重连、存活探测、连接状态机； 2. 周期性批量读取 —— 由**基类 `DeviceBase`/`DeviceRoot` 的波次循环**完成 （`BuildPlan` 建块 ＋ `ExecutePlanByRate` 多速率调度），减少网络往返； ⚠️【2026-11-11 订正】原写「通过 `BatchEngine` 合并」—— **该类已于 `24bfaaba` 删除** （它是"从未接线的第二采集引擎"，零引用），采集引擎已收敛为 `DeviceRoot` 单一实现 ✗→✓； 3. QoS 分级写入 —— 安全写（联锁/急停）绝对优先，普通写可合并去重； 4. 心跳保活 —— 定期向 PLC 写入翻转位，让对端判定上位机是否存活。

    与 DeviceBase 的区别：DevicePro 内置写队列和连接状态机， 适用于需要"安全写入优先 + 普通写入去重"的关键控制场景（如配方下发、报警复位）； DeviceBase 则适合只读采集或对延迟不敏感的辅助回路。

    StartSelfBackgroundTasks()

    启动本类专属的后台任务。 统一写入处理器（WriteProcessor）将安全写和普通写合并在同一循环中处理， 确保安全写（QoS 高优先级）具有绝对优先权。

    幂等守卫：每个任务启动前检查字段为 null 或 IsCompleted， 确保 Start() 多次调用不会重复创建后台任务。

    当前启动的后台任务：

    • _safetyWriteProcessor — 统一写入处理循环。将安全写（急停、联锁）和普通写合并分发，安全写可中途插队。
    • _livelinessTask — 协议级存活探测。在主读取循环空闲时发送极小包，检测设备端是否仍在正常工作。

    Remarks

    🔑【2026-11-09 全局审查，A-267】写成功后【不】立即回写缓存、不调用 OnTagWritten 扩展点（与 DeviceBase.Write 刻意不同）✓

    **为什么**：本类的写是**队列语义** —— "返回 `IsSuccess=true`" 只表示**已入队**， **不代表 PLC 已收到并生效** ✗。若此时就把 `tag.CurrentValue` 改成写入值并标 `Quality=Good`， 等于**谎报设备状态**（现场会看到"缓存已变、实际未变"）✗✗

    ✅ **正确的最终一致路径**：写请求由队列消费后真正下发 ⇒ 下一轮**批读**从 PLC 读回真值 ⇒ 由采集线程写 `localCache` 与 `tag.CurrentValue`（见 `DeviceRoot` 的 `EvaluateTagChange` 之后） ⇒ 因此**写完立刻读缓存可能仍是旧值，属预期** ✓

    ⚠️ **与 `DeviceBase.Write` 的差异**（同为写，语义不同，勿"统一"✗）：

    • `DeviceBase.Write`／`WriteAsync`：**同步写**、PLC 已确认 ⇒ **立即**回写当值 ＋ 调用 `OnTagWritten` 扩展点 ✓
    • `DevicePro.Write`／`WriteAsync`：**队列写**、未确认 ⇒ **不**回写、**不**调用扩展点，等批读刷新 ✓

    需要"写完立刻拿到确认值"⇒ 用 `DeviceBase` 家族，或写后显式 `ReadResult<T>` 穿透读 ✓

    ⚠️ **术语澄清（勿误解为"有事件"）**：`OnTagWritten` 在 `DeviceBase` 里是 **`protected virtual` 的【空实现】**（注释原文：「写入成功后的**扩展点**：子类**可覆写**」）✗⇒✓ ⇒ **基类不会因此派发任何事件** ✓；全仓**也没有**"写成功"事件 —— 写成功是通过 `DeviceResult` **返回值**告知调用方的 ✓ ⇒ 若需要"写成功回调"，请**覆写 `OnTagWritten`** 或自行轮询 `localCache` ✓
