    EndianConverter

    字节序：小端（DCBA）。

    🔴 【2026-11-03 修 ✗→✓：原为 `BigEndianConverter`，实测证明连 int16 都错】

    实测证据（双向，真实收发，2026-11-03 收尾交叉测试）： 

    我方写 D600 int16 0x1234 → HSL 读得 0x3412   ❌ 字节被交换
HSL  写 D602 int16 0x1234 → 我方读得 0x3412   ❌ 双向都错
HSL  写 int32 0x12345678 → 内存落 78-56-34-12  （完全反转 = DCBA）

    ⚠️ 注意：本协议连 int16 都错（不是"单字对、双字错"）， 与 Memobus/Yokogawa/KeyenceNano 那三例（int16 对、int32 字交换）不同型， 修法也不同——那三例用 CdabEndianConverter，本协议必须用 LittleEndianConverter。

    依据（逐层，可复现）：HSL 13.0.3 原件 `HslCommunication.Profinet.Inovance/InovanceEasyNet.cs` 构造： base.ByteTransform = new RegularByteTransform();； 而 RegularByteTransform() 无参构造默认 DataFormat = DCBA； 其 ByteTransDataFormat2 在 DCBA 分支是原样复制（小端） ⇒ HSL 发出的 int16 载荷是小端。本驱动原先用大端 ⇒ 与 HSL 相反 ✗

    🔴 原注释「与 HAL 一致」是错的 —— 无任何依据，已删除 ✗

    ⚠️ 证据性质（必须如实说明）： 官方规格 `docs/evidence/19011157-SC_A21...pdf` **§16.4（p.661）只定义了 指令码 / 子指令 / 软元件范围，未定义载荷字节序** ✗ ⇒ 本结论依据是 HSL 单源 + 仿真器线序 ⇒ B 级， 不是"官方已确证"，真机验证仍缺 ✗

    WriteAsync(string, bool[])

    位区 bool 写（2026-11-16 永久修复：位打包 ＋ 精确点数）。

    【为什么必须单独覆写（而不是复用 `WriteBytesCore`）】 基类 `WriteAsync(string, bool[])` 把 `bool[]` 转成 **1 字节/点** 的 `byte[]` （`new byte[value.Length]`），而 EasyNet 位区线上格式是 **1 位/点（位打包）**： · HSL 13.0.3 `InovanceEasyNet.cs` `BuildWriteCommand(string, bool[])`： `byte[] array = value.ToByteArray();`（`SoftBasic.BoolArrayToByte` ⇒ `ceil(N/8)` 字节） 且 `array2[18..20] = value.Length`（**点数，不乘 8**）； · 仿真器 `InovanceEasyNetServer.cs` 写分支：`requiredBytes = (raw + 7) / 8`、 `WriteBits(area, addr, bitCount: raw, packed)` ⇒ 同样认定 `raw = 位数`、载荷位打包。 ⇒ 若走字节路径，`raw` 会变成 `N * 8`，点 `i` 被写到点 `8i`、并清零相邻 7 点（**静默错值**）。

    【分片】按**点数**切（位区上限 `MaxBitPoints = 3584`，取 ASCII 保守值）； 每片重新打包，`raw` = 本片**精确点数**（不是 `ceil * 8`）。

    【字区不走这里】`IsWord` 时退回字节路径（语义未变）。
