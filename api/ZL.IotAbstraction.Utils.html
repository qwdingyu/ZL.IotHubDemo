    AsyncAutoResetEvent

    异步自动重置事件（Async AutoResetEvent）。

    在工控采集场景中，常用于"有新数据到达，唤醒等待的消费者线程"这类生产者-消费者模式。 与 System.Threading.AutoResetEvent 类似，但完全基于 async/await， 不会阻塞线程池线程，适合高并发采集场景下作为信号通知机制。

    核心语义：调用 Set() 后，下一个（且仅一个）WaitAsync(CancellationToken) 调用会立即返回， 之后事件自动重置为未触发状态。

    AsyncTimer

    基于 async/await 的周期定时器。

    在工控场景中常用于：心跳发送、连接保活、周期性巡检等定时任务。 相比 System.Timers.Timer，它不会在线程池上触发回调， 而是在 async 上下文中顺序执行，天然避免了回调重入问题。

    注意：此定时器会在上一次回调完成后才开始下一次等待， 因此实际间隔 = interval + 回调耗时，适合"固定间隔"而非"固定频率"场景。

    CancellationTokenExtensions

    System.Threading.CancellationToken 的扩展方法集合。 在工控采集循环中，经常需要"等待一段时间或者被取消"这类模式， 此扩展将其封装为一行调用，简化退避/重连/心跳等循环的编写。

    【2026-11-05 收为 internal】与 `ZL.PFLite.TaskKit.CancellationTokenExtensions` **同名但成员完全不同** （本处仅 WaitCancellationOrDelay；PFLite 是 AsTask/WithTimeout）⇒ 作为 public 会让 "同时引用 Engine + PFLite"的消费者裸写该类名时 **CS0104 歧义** ✗；本类型仅引擎内部使用 ⇒ 收为 internal ✓

    CustomPeriodicTimer

    跨框架版本的周期性计时器（Polyfill）。

    在工控采集主循环中，通常以 while(await timer.WaitForNextTickAsync()) 的方式 驱动采集周期。此计时器统一了不同 .NET 版本下的 API 差异：

    • .NET 6+：直接委托给微软原生的 System.Threading.PeriodicTimer（高性能、零分配）

    • .NET Standard 2.0 / .NET Framework 4.8：基于 System.Threading.Timer + TCS 自行实现

    这样上层业务代码可以用同一套写法，而无需关心运行时的框架版本。

    LogThrottle

    日志时间节流：同一 key 在 DefaultInterval 内最多放行一次。

    【为什么要有这个类 —— 2026-10-17 全局复盘】 本仓此前"日志刷屏"的治理是**各写各的**：DeviceRoot 用内联的 _lastHealthLogTicks（周期健康日志 60s）、DriverFactory 用 volatile 的 "只发一次"标志、而失败路径（Ping 告警/块读超时/块读异常）**什么都没用** ⇒ 按周期刷屏。 第一次修复时我把同一段节流逻辑**复制到了两个类**里 —— 那正是本仓反复出问题的形态 ⇒ 复盘后收敛为**本类唯一实现**。

    【设计取舍】 · **无锁**：极端并发下最多多打一条（日志重复无害），换取采集热路径零锁竞争 —— 与 DriverFactory 的"重复警告无害"取舍一致； · **键的基数有限**（块地址 / 固定名）⇒ 内存有界，无需淘汰； · 间隔是**类级默认值**（不是每个实例各一个旋钮）⇒ 全仓只有一个口径，避免"两处阈值不一致"。

    ValueScale

    工程量换算纯函数工具：工程值 = 原始值 × factor + offset。

    典型用法（应用层/展示层，不在 IotHub 内核）：

    // 传感器：原始量 2500 表示 25.00 ℃ ⇒ factor = 0.01, offset = 0
double eng = ValueScale.Apply(2500, 0.01);

// 4~20mA 变送器：原始 0..4095 对应 -40..+80 ℃
//   factor = 120.0 / 4095, offset = -40
double t = ValueScale.Apply(raw, 120.0 / 4095.0, -40.0);

// 写回时反解（保证与读方向对称）
double rawToWrite = ValueScale.Reverse(t, 120.0 / 4095.0, -40.0);

    🔴 设计约束（勿改）：

    1. **只做线性变换**。非线性（查表、开方、分段）请在应用层自己做 —— 一旦这里接受任意函数，就等于在 IotHub 里重新引入了"表达式引擎"， 而这正是明确拒绝的东西。
    2. 不做类型转换。输入输出都是 double， 要 float/short 请调用方自行转换 —— 避免在这里引入"取整策略"这种隐含语义。
    3. Reverse 不做除零保护以外的任何裁剪。返回值可能超出 PLC 数据类型范围， 是否截断由调用方决定（静默截断 = 制造假数据）。

    为什么是静态类而不是实例：无状态、无配置、可并发； 需要"带配置的换算器"时，调用方持有 (factor, offset) 即可。
