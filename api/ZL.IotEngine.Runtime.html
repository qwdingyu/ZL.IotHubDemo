    BackpressureMonitor

    通知管道背压监控器 —— 检测 PlcNotificationHub 的事件丢弃并主动告警。

    【工业背景】 PlcNotificationHub 使用 DropOldest 策略：当消费端处理速度跟不上时， 丢弃最旧的事件而非阻塞生产端。这在工控场景是合理的（实时性优先）， 但必须有 Drop 告警——否则数据静默丢失，现场工程师无法感知。

    【设计】

    • 定时轮询 PlcNotificationHub 的 Metrics 快照
    • 计算丢弃增量（delta），仅在丢弃数增长时告警
    • 30 秒冷却期，防止告警风暴

    PlcConnectionThrottle

    PLC 连接限流器 —— 防止启动时多个 PLC 同时发起 TCP SYN 导致内核 backlog 打满。

    【工业背景】 当 40 台 PLC 同时发起 TCP 连接时，操作系统内核的 SYN backlog 队列会被瞬间打满， 导致部分 SYN 包丢失、TCP 重传（3 秒 RTO），连接延迟从 10ms 暴增到 3+ 秒。 Kepware 的做法：按序逐个连接，默认间隔 500ms，可配置。

    【设计】

    • 全局单例，通过 Initialize 配置并发上限
    • SemaphoreSlim 限流 + 连接间固定间隔，确保 TCP 连接有序建立
    • Release 在 Delay 之前：先释放 slot 让后续连接排队，再延迟，最大化吞吐
    • 所有 PLC 的首次连接和重连都应经过此限流器

    PlcEventDispatcher

    PLC 事件分发器 —— 将事件分发从 deviceLock 保护范围内解耦出来。

    【解决的问题】 当前架构中，ProcessValueChanges 在 deviceLock 保护范围内同步 Invoke 事件。 这意味着：锁持有时间 = IO读取 + 变更检测 + 事件分发。 如果下游订阅者（如写入数据库）慢，整个 PLC 的采集周期被拖慢。

    【设计 — v6 有界 DropOldest + 背压可观测（2026-10-31 头注释订正）】

    🔴 现行语义以构造器为准：事件通道是有界（10000 批）DropOldest —— 极端背压（下游持续慢于采集）时会丢弃最旧批次并计数，不是零丢失 ✗→✓ （原头注释停留在 v5「无界 + 零丢失」，与 v6 实现不符；零丢失需要持久化队列兜底， 见 TryEnqueueTrigger 的说明）。头注释承诺后人会依赖，故必须与实现一致 ✓

    演进（每轮都有实测依据）： v1 (Task.Run fire-and-forget): 4MB/s 内存泄漏 → ❌ v2 (同步内联): 消除泄漏但慢订阅者阻塞 Channel 消费 → ❌ v3 (Semaphore 有界并发 + DropOldest): 内存安全但 66.7% 事件被丢弃 → ❌ 不适合汽车制造 v4 (无界 Channel + 同步分发): 零丢失，但慢订阅者可导致 OOM → ❌ 缺少内存保护 v5 (无界 Channel + 高水位告警 + LogCallback): 零丢失 + OOM 预警 → ⚠️ 仍会 OOM v6 (有界 Channel + DropOldest + 限流告警 + LogCallback): 内存有界 + 丢弃可观测 → ✅ 现行

    数据流： BatchReadLoop (持有 deviceLock) → 读取 PLC → 变更检测 → _eventChannel.Writer.TryWrite(changes) [有界 10000 批，满则丢最旧] EventDispatchLoop (独立线程，不持有 deviceLock) → _eventChannel.Reader → PlcNotificationHub.PublishTagChanges(changes) [同步分发]

    PlcFleetManager

    PLC 集群管理器 —— 多 PLC 场景下的启动编排与运行时协调中枢。

    【设计意图】 当系统需要同时管理 30-40 台 PLC 时，简单的"逐个 new 出来"会导致：

    1. ThreadPool 饥饿：40×8=320 个 Task 同时竞争默认 16 线程
    2. SYN 风暴：40 个 TCP 连接同时发起
    3. 无启动状态可见性：不知道哪些 PLC 启动成功、哪些失败

    PlcFleetManager 解决这三个问题：

    • 启动前预热 ThreadPool（消除饥饿）
    • 分批启动 PLC（消除 SYN 风暴，通过 PlcConnectionThrottle）
    • 提供启动状态报告（可观测性）

    【使用方式】 在应用启动入口（Program.cs / Service 入口）调用： PlcFleetManager.Initialize(estimatedPlcCount: 40); 然后在创建 PLC 实例时通过 RegisterDevice 注册。

    PlcHealthCheck

    PLC 采集系统健康检查器——零外部依赖，基于已有诊断数据聚合。

    使用场景： - 容器编排 HealthCheck 探针（K8s liveness/readiness） - 运维看板轮询 - 定时告警判断

    设计原则： - 不新增后台线程，按需查询 - 不修改 DeviceRoot/DevicePro，通过 Func 委托注入诊断数据 - 判定阈值可配置
