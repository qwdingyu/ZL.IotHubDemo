    Class SafetyWriteRequest

    安全写入请求——不可合并、必须保证执行的高优先级写入操作。

    与 NormalWriteRequest 的核心区别： - NormalWriteRequest 可被合并去重（同一地址只保留最新值），适用于 HMI 手动操作； - SafetyWriteRequest 走**高优先级安全写队列**（可插队普通写），适用于安全联锁、急停复位等关键操作。

    ⚠️ **但"不可丢弃"目前不成立（2026-10-31 实测）**：安全写 Channel 容量 200、 `FullMode = DropOldest` ⇒ **队列满时会静默丢弃最旧的一条**， 且**没有告警**（`DevicePro` 注释声称有告警，代码中不存在）。 调用方不会挂死（有 `SafetyWriteTimeout`，默认 2000ms 兜底），但会收到 「写入超时或被取消」——**真实原因可能是"队列满被丢弃"** ✗

    支持"操作序列"（Sequence）：在工控场景中，某些操作需要按严格顺序执行 （如先关闭阀门 → 再停止泵 → 最后打开排放阀）， ⚠️ **排序尚未实现（2026-10-31 实测，勿再误传）**：`SequenceId` / `SequenceOrder` 目前**只被赋值、从未被读取**；安全写 Channel 是 FIFO， 执行顺序**只取决于入队先后**，与 `SequenceOrder` 无关 ✗

    ⇒ 需要"先关阀 → 再停泵 → 最后开排放阀"这类**严格顺序**时， **调用方必须串行入队并逐条等待结果**，不能靠并发入队 + `SequenceOrder` 排序。

    复核命令（阳性对照：赋值应有 2 处；读取应为 0）： grep -rn "SequenceOrder =\|SequenceId =" ZL.IotEngine/ tests/ grep -rnE "\.SequenceOrder|\.SequenceId" ZL.IotEngine/ tests/ | grep -v "SequenceOrder =\|SequenceId ="

    内置重试机制：通过 executionAttempts 原子计数器跟踪执行次数， 最多重试 3 次（工控通讯偶发超时时需要自动重试以保证可靠性）。

    RequestTickMs

    单调时钟时间戳（Stopwatch.GetTimestamp() 原始刻度） —— 用于超时判定。

    🔴🔴【2026-11-11 **7×24 健壮性**】超时判定原用 `DateTime.UtcNow - RequestTime` ✗： **系统时钟被 NTP 回拨**时差会**变负** ⇒ `ageMs > _safetyWriteTimeout` **恒假** ⇒ **过期的安全写指令会被执行**（如 5 秒前的"急停复位"）✗✗ —— **安全事故级** ✗

    **为什么保留 `RequestTime`**：它是**公开 API**（对接方可能用于审计/展示）， 删或改类型会破坏兼容 ⇒ **追加**本单调字段，**只用于内部超时计算** ✓

    ⚠️ **为什么用 `Stopwatch` 而不是 `Environment.TickCount64`**： 后者**只在 net8.0+ 存在**，而 `ZL.IotEngine` 多目标含 `netstandard2.0` / `net48` ⇒ 会 **CS0117**（我第一版就踩了这个坑 ✗，正是 AGENTS §21.5 记载的形态）✗→✓ `Stopwatch.GetTimestamp()` **全 TFM 可用**且**单调**（不受系统时钟调整影响）✓ 差值换算：`(nowTicks - startTicks) * 1000.0 / Stopwatch.Frequency` 毫秒

    SafetyLevel

    安全等级，默认为 ProcessControl。

    ⚠️ **当前实际作用（2026-10-31 实测，勿再误传）**：**仅用于失败日志** （DevicePro 中 if (SafetyLevel <= SafetyInterlock) Log(...)）✗ 不参与队列优先级排序，也不参与是否重试的判定 —— 优先级只有"安全写 vs 普通写"两级；重试对所有等级一律最多 3 次。
