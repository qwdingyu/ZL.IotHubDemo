    Class SiemensS7Driver

    西门子 S7 协议纯 C# 原生驱动 —— 直接基于 TCP Socket 实现 ISO-on-TCP + S7 通信， 无需 S7.Net / Sharp7 / HSL 等任何第三方依赖。

    【协议要点】

    • ISO-on-TCP (RFC 1006)：TPKT(4B) + COTP(3~7B) 头封装
    • 三次握手：Connect Request(CR) → Connect Confirm(CC) → S7 Communication Setup
    • 读取命令：Header(4B) + S7 Header(18B) + Parameter(12B/条)
    • 写入命令：Header(4B) + S7 Header(18B) + Parameter(16B/条) + Data
    • 每个地址项 12 字节参数（读取）或 16+ 字节（写入）
    • 响应解析：返回数据在报文末尾，长度由响应头第 2-3 字节指示

    【地址格式】 DB1.0 数据块 1，字节 0 DB1.DBX0.0 数据块 1，位 0.0（X 标记可省略） M0.0 存储区，字节 0 位 0 I0.0 输入区，字节 0 位 0（E0.0 德文兼容） Q0.0 输出区，字节 0 位 0（A0.0 德文兼容） T1 定时器 C1 计数器 V0 V 区（S7-200 兼容）

    CheckPduReferenceEnabled

    是否校验响应的 PDU Reference 与请求一致（默认 true）。

    Declaration
    public bool CheckPduReferenceEnabled { get; set; }
    Property Value
    Type Description
    bool
    Remarks

    【作用】开启时，若响应的 PDU Reference（[11..12]）与本次请求不符， 立即失败并丢弃连接。这能拦住「上次请求超时后、迟到的响应留在流里， 被下一次请求当作本次结果返回」的静默错值 —— 与 docs/82、docs/83 记录的事故同类。

    【何时需要关闭】真实西门子 PLC 按 S7comm 规范必须回显请求的 PDU Reference （HSL 客户端的 S7Message.CheckMessageMatch 也依赖这一点）， 但**部分仿真器/模拟器不回显**，例如 HSL 自带的 SiemensS7Server 把响应模板里的 PDU Reference 硬编码为 0x0001 （见 SiemensS7Server.cs 的 HexStringToBytes 模板）。 对接这类服务端时需将本属性置为 false，否则第二次请求起就会失败。

    【对齐 HSL】HSL 为同样的场景提供了 S7Message.CheckMessage 开关 （默认 true，注释说明"设置为 false 则不检查消息合法性，适用于一些特殊的协议解析需求"）。 本属性与之等价。

    ReadBool(string)

    读取布尔值。

    位地址（"M0.3"、"DB1.DBX0.1"、"DB1.0.3"）按其位偏移读取； 未写位偏移的地址（"M0"、"DB1.0"）隐式视为 bit 0，等价于 "M0.0" / "DB1.DBX0.0"。

    【为何隐式 bit 0 而非报错】历史标签表中大量 bool 点位写作 "DB1.0"， 若一律拒绝会导致握手/心跳/就绪确认在升级后集体中断； 而按"整字节非零即 true"解释又与写入侧的位语义不对称。 统一按 bit 0 解释使读写闭环，且与 PlcValueExtractor 批量提取路径 （bool 用 parsed.BitOffset，缺省为 0）行为一致。

    ReadByteAsync(string)

    读取单个字节（8 位无符号）。

    [!!]【2026-11-12 补声明 —— 修一处接口遗漏】 本接口原有成对的 ReadBool/Int16/UInt16/Int32/UInt32/Int64/UInt64/Float/Double （同步+异步各一套），唯独漏了 byte。

    遗漏造成的实际后果：ZL.IotDriver/Siemens/SiemensS7Driver 实现了 ReadByte/ReadByteAsync（它有该语义需求），但接口上没有声明 ⇒ ZL.IotEngine 只能用 ((dynamic)Device).ReadByteAsync(...) 绕过接口 去调用（DeviceBase.cs、DevicePro.cs）。这带来三重代价：

    1. 类型不安全：方法名拼错要到运行时才炸（编译器无法发现）；
    2. 重构失效：改方法名时 IDE 找不到引用；
    3. 强制引入 Microsoft.CSharp 依赖（dynamic 调用点需要 binder）。

    并且它掩盖了"其余 24 个实现都不支持单字节读"这个事实。

    为什么补进接口是安全的（2026-11-12 实测确认）： SiemensS7Driver 的实现是纯薄包装，没有任何协议专属逻辑 —— DeviceResult<byte>.FromBytes(ReadBytes(address, 1), b => b[0])， 与同文件 ReadInt16Async（FromBytes(ReadBytesAsync(addr,2), b => { Array.Reverse(b); ... })） 模式完全一致。而 ReadBytesAsync 本就在本接口上 ⇒ 任何实现都能用同一行得到等价语义。 另实测：25 个实现类全部已有 ReadBytesAsync（缺少 0 个）⇒ 前提成立。

    [!] 为什么没有用"默认接口实现(DIM)"省掉逐个实现： 实测 netstandard2.0 目标报 error CS8701: 目标运行时不支持默认接口实现（DIM 需 .NET Core 3.0+ 运行时）。 本程序集是 netstandard2.0;net48;net8.0;net10.0 四目标 ⇒ 前两个目标都无法使用 DIM，因此必须由各实现显式提供。

    实现约定：若某驱动的协议语义上确实无单字节读， 应显式返回 Fail(..., DeviceFailureKind.NotSupported)， 不要静默降级为 ReadBytes(address, 1) —— 显式拒绝优于隐式降级。

    完整分析与可复制方法论。

    [?] 要读 8 位有符号（SINT / SBYTE）怎么办： 本接口不提供 ReadSByteAsync（行业惯例如此：HSL / plc4x 同样只暴露 ReadByte，因为协议层 8 位就是 1 个字节，符号是解释而非传输语义）。 请用泛型扩展（ZL.IotEngine，需 using ZL.IotEngine.Orchestration;）： 

    var r = await device.ReadAsync<sbyte>("DB1.DBB0");   // ⇒ DeviceResult<sbyte>

    它按 Marshal.SizeOf<sbyte>() == 1 读 1 字节，再由 EndianConverter.Convert<sbyte> 解释为有符号 [OK]（四个 EndianConverter 实现均已支持）。 批量读同理：device.ReadArrayAsync<sbyte>(addr, count)。
