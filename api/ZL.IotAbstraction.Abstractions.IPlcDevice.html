    IsConnected

    [!!][!!]【2026-11-12 补全契约】当前是否已连接 —— 缓存状态，不是实时探测。

    **本属性是公开 API 面**：外部消费者（UseThink.Iot / tmom）会直接用它判断设备可用性 ⇒ 按 `AGENTS §20.1`「搜不到引用 ≠ 没有引用」，**不得**因本仓无调用方就当它可省 [X]

    [!!] **契约（实现方与调用方都必须遵守）**：

    • ① 它是"缓存状态"，不是"实时探测" —— 只反映 **最近一次 ConnectServer()/ConnectClose() 或最近一次操作的结果**。 网络中途断开（拔网线、对端重启）**不保证立即变 `false`** [!]
    • ② 判断"能不能读写"必须看操作结果（`DeviceResult.IsSuccess`）， 不得仅凭本属性做重连决策 [OK] （与 `libplctag` / `S7.Net` / `HslCommunication` 等主流 PLC 库口径一致 —— 它们的连接状态同样是近似值）
    • ③ 本接口不提供自动重连 —— 重连策略由**调用方**（编排层/宿主）负责： 在操作失败后按自己的退避策略调 ConnectServer() [OK]
    • ④ 实现方应尽量让状态"及时"：推荐在**操作结果转换的汇聚点**更新 （成功 ⇒ `true`；**连接级**失败 ⇒ `false`；**协议级**失败 ⇒ 不动）。 参考实现：`ZL.IotHub.X/Hsl/HslToDeviceAdapter.UpdateConnectionState` （实测 HSL 断线 `ErrorCode = -1`、协议错误 `= 10`、默认 `= 10000`）[OK]
    • ⑤ 方向必须保守：宁可偶尔误判"已断"（多一次重连）， 也**不要**在真断线时仍报 `true` —— 后者会让调用方跳过重连 ⇒ **设备永久不可用** [X][X]

    [!] **已知能力边界**：UDP 无连接概念、串口无链路状态 ⇒ 这两类实现只能靠 "操作失败"推断，精度**低于** TCP ⇒ 调用方对 UDP/串口应更依赖操作结果 [OK]

    ConnectClose()

    关闭连接（幂等：未连接时也应返回成功）。

    [!] 实现方**必须**释放底层 socket/串口，否则端口泄漏会拖垮后续测试与重连 [OK]

    [!!] **本方法就是本接口的资源释放契约** —— 不要再给 IPlcDevice 加 IDisposable / IAsyncDisposable。

    【为什么（三条实测依据，勿凭印象推翻）】

    1. **框架已调用它**：`DeviceBase.Dispose()`（`ZL.IotEngine/Orchestration/DeviceBase.cs`） 方法体内有 `Device?.ConnectClose();` ⇒ 释放闭环是 `Dispose()` → `ConnectClose()` → 底层 `Dispose()/Close()`，**不需要第二个释放入口**。

      [!!]【2026-11-13 补充实测】该闭环只覆盖 **`Dispose`**；**"重连替换 `Device`"** 是另一条路径， 曾**不关旧实例**（`DeviceRoot.Device` 是 public 字段，赋值即静默丢弃）⇒ 每次重连滞留 1 个 TCP 句柄直到 GC（实测 lsof：+1/次，强制 GC 归零）。 已于 2026-11-13 在 `NativeUnifiedDriver.Connect()` / `HslUnifiedDriver.Connect()` 补 `ConnectClose()`； 完整证据。

    2. **`IAsyncDisposable` 需要额外依赖，且收益为零**： `netstandard2.0` / `net48` 的 BCL **不含** `System.IAsyncDisposable`， 要用必须给本包新增 `Microsoft.Bcl.AsyncInterfaces` 依赖 （旁证：`ZL.IotHub.Bridges` 因 SignalR 传递**已有**该包，其 `SignalRPlcBridgeSink` 在 net48 / netstandard2.0 **实测可编译** ⇒ 不是"不可能"，而是"要付一个依赖的代价"）。 但见下条：底层无异步释放 ⇒ **不值得付**。

      [X]【2026-11-13 订正】本节原写「在本仓目标框架上**不可用**」并附"独立探针报 4 个错误"—— 该探针工程**没有** `Microsoft.Bcl.AsyncInterfaces`，测的是"裸环境"而非"本仓"[X] 结论（不加 `IAsyncDisposable`）不变，**论据**已改为"依赖代价 + 零收益" [OK]

    3. **底层资源本身没有异步释放**：实测 `TcpClient`、`NModbus.IModbusMaster`(3.0.83) 的 `IAsyncDisposable` 均为 `False`；`S7.Net.Plc`、`SerialPort` 只有同步 `Close()`/`Dispose(bool)` ⇒ 即使加 `DisposeAsync()`，内部也只能调同步释放，**零收益**。

    【若给接口加 `IDisposable` 的代价（为什么不做）】 `ZL.IotAbstraction` 是**已发布 NuGet 包**（2.3.0）⇒ 主版本破坏性变更； 跨仓消费者（UseThink.Iot / tmom）升级即断； 且形成 `ConnectClose()` 与 `Dispose()` **两条释放路径** ⇒ 需额外防重复释放。

    [X]【2026-11-13 订正】原文写「全部实现类**立即编译失败**（本仓实测 54 个：生产 16 ＋ 测试 38）」—— **计数口径错**：54 是"出现 `IPlcDevice` 的类型数"，不是"会 CS0535 的类数"。 实测：生产侧**直接声明** `: IPlcDevice` 的类共 **15** 个，其中 **11** 个**已实现 `IDisposable`** （`NativeDriverBase`/`SiemensS7Driver`/`MitsubishiMcDriver`/`BeckhoffAdsNet`…）⇒ 不会因接口新增而失败； 真正会失败的只有 `NModbusDeviceAdapter`/`S7PlusDeviceAdapter`/`HslToDeviceAdapter` ＋ 测试侧直接声明且无 `Dispose` 的约 6 个文件（继承 `StubPlcDeviceBase` 等的子类**不受影响**）。 ⇒ **真正代价是 SemVer 破坏 + 跨仓断链**（上面两条），不是"54 个编译失败" [OK]

    【回归防护】门禁 `scripts/audit/check_connect_close_release.py`（㊸） 静态检查每个 `ConnectClose()` 方法体**必须**含释放调用 （直接 `.Dispose()/.Close()/= null`，或间接调用名字含 `Close/Dispose/Release/Cleanup/Shutdown/Teardown/Destroy` 的辅助方法）。

    ReadByteAsync(string)

    读取单个字节（8 位无符号）。

    [!!]【2026-11-12 补声明 —— 修一处接口遗漏】 本接口原有成对的 ReadBool/Int16/UInt16/Int32/UInt32/Int64/UInt64/Float/Double （同步+异步各一套），唯独漏了 byte。

    遗漏造成的实际后果：ZL.IotDriver/Siemens/SiemensS7Driver 实现了 ReadByte/ReadByteAsync（它有该语义需求），但接口上没有声明 ⇒ ZL.IotEngine 只能用 ((dynamic)Device).ReadByteAsync(...) 绕过接口 去调用（DeviceBase.cs、DevicePro.cs）。这带来三重代价：

    1. 类型不安全：方法名拼错要到运行时才炸（编译器无法发现）；
    2. 重构失效：改方法名时 IDE 找不到引用；
    3. 强制引入 Microsoft.CSharp 依赖（dynamic 调用点需要 binder）。

    并且它掩盖了"其余 24 个实现都不支持单字节读"这个事实。

    为什么补进接口是安全的（2026-11-12 实测确认）： SiemensS7Driver 的实现是纯薄包装，没有任何协议专属逻辑 —— DeviceResult<byte>.FromBytes(ReadBytes(address, 1), b => b[0])， 与同文件 ReadInt16Async（FromBytes(ReadBytesAsync(addr,2), b => { Array.Reverse(b); ... })） 模式完全一致。而 ReadBytesAsync 本就在本接口上 ⇒ 任何实现都能用同一行得到等价语义。 另实测：25 个实现类全部已有 ReadBytesAsync（缺少 0 个）⇒ 前提成立。

    [!] 为什么没有用"默认接口实现(DIM)"省掉逐个实现： 实测 netstandard2.0 目标报 error CS8701: 目标运行时不支持默认接口实现（DIM 需 .NET Core 3.0+ 运行时）。 本程序集是 netstandard2.0;net48;net8.0;net10.0 四目标 ⇒ 前两个目标都无法使用 DIM，因此必须由各实现显式提供。

    实现约定：若某驱动的协议语义上确实无单字节读， 应显式返回 Fail(..., DeviceFailureKind.NotSupported)， 不要静默降级为 ReadBytes(address, 1) —— 显式拒绝优于隐式降级。

    完整分析与可复制方法论。

    [?] 要读 8 位有符号（SINT / SBYTE）怎么办： 本接口不提供 ReadSByteAsync（行业惯例如此：HSL / plc4x 同样只暴露 ReadByte，因为协议层 8 位就是 1 个字节，符号是解释而非传输语义）。 请用泛型扩展（ZL.IotEngine，需 using ZL.IotEngine.Orchestration;）： 

    var r = await device.ReadAsync<sbyte>("DB1.DBB0");   // ⇒ DeviceResult<sbyte>

    它按 Marshal.SizeOf<sbyte>() == 1 读 1 字节，再由 EndianConverter.Convert<sbyte> 解释为有符号 [OK]（四个 EndianConverter 实现均已支持）。 批量读同理：device.ReadArrayAsync<sbyte>(addr, count)。

    WriteAsync(string, byte)

    写单个字节（8 位无符号）—— 与 ReadByteAsync(string) 对称。

    [!!][!!]【2026-11-12 新增】**为什么必须进接口**： `byte` 是**一等数据类型**（`PlcDataTypeMap["byte"]`，点表可配 `DataTypeCode="byte"`）， 但本接口此前只有 9 个标量写重载（bool/short/ushort/int/uint/long/ulong/float/double）， **独缺 `byte`** ⇒ 引擎只能走 `WriteAsync(string, object)` 兜底， 而 `NativeDriverBase` 的 object 分派 switch **没有 `byte` 分支**（实测） ⇒ **27 个 Native 驱动 ＋ 10 个 Serial 驱动根本不能写 byte 标签**（功能缺口，非"不好用"）[X]

    **契约（写 1 个字节）**：实现应把 `value` 作为**一个字节**下发； 若该协议在语义上无法表达"单字节写"（例如字寻址协议的寄存器是 16 位）， **必须明确失败并给出改法**（提示改配 `short` 或 `byte[]`）， **不得**静默写成 2 字节、也不得静默截断 [X]（AGENTS：fail-loud 优于隐式降级）。

    [!] **实现者注意**：默认实现可直接 `return WriteBytesAsync(address, new[] { value });` （`WriteBytesAsync` 是本接口成员，长度单位恒为**字节**，见 AGENTS §21.1）。
