    Class PlcStringReadHelper

    PLC 字符串读取的共享 纯函数（读侧唯一解析源，与写侧 PlcStringWriteHelper 成对）。

    职责边界：只负责「把一段已经读到的字节缓冲，按 StringKind 布局与 encoding 解析成 .NET string」， 不负责传输（读几段、从哪开始读、读多长）。传输策略由各调用方决定。

    【2026-10-17 二次收口】此前"唯一解码源"只完成了 1/4 ✗： 仅 PlcValueExtractor 委托到这里，而 DevicePro.ReadStringAsync<T> 与 DeviceBase.ReadFromDeviceInternal 各自内联一套头剥离 + 解码 + 修剪 ✗， BatchMonitor.ReadStringAsync 更是"先让驱动把地址偏移 +2 拿到无头内容、再对 string 剥一次头" ✗。 实测后果：同一个 S7String 标签、同一份 PLC 数据，四条读路径给出不同的值 ✗。

    【统一口径（四条读路径共同遵守）】 ① 头剥离只发生在原始字节上，且只发生一次 —— 对已解码的 string 再剥头是结构错误 ✗； ② 内容区只按布局声明的长度取（Raw=声明长度、S7String=Byte1、S7WString=实际字数×2）； ③ 不按内嵌 \0 截断（S7 STRING 允许内嵌 NUL，按首 NUL 截会丢数据）； ④ 只做 TrimEnd('\0')（尾部填充），不去首尾空白、不删内部 CR/LF。

    DecodeRaw(byte[], int, int, Encoding, bool)

    同 DecodeRaw(byte[], int, int, Encoding)，但可选择截断策略 ✓。

    【两套语义并存的原因】本仓历史上有两种"结尾 NUL"处理 ✗： · **IEC 语义**：在**首个** \0 处截断 ✓（`NativeDriverBase` / `SerialDriverBase` 的 `ReadString` 长期如此 ✓）； · **裁尾语义**：只裁掉**尾部** \0 ✓，保留内容中的内部 \0 ✓（本方法原行为 ✓）。 二者只在"**内容含内部 NUL 且其后仍有非 NUL 字节**"时结果不同 ✗ （纯填充、全 0、空缓冲三种场景**完全一致** ✓）。

    【为什么必须两套都留】对**定长/RAW 字符串字段**（如 Modbus 保持区 ✓）， 填充之后未必全 0（PLC 可能只覆盖了前缀 ✗）⇒ **首个 NUL 截断**才是正确语义 ✓； 而对**带长度头**的字段（S7 STRING ✓），内部 \0 是合法内容 ✗ ⇒ 必须用**裁尾** ✓。 ⇒ 由调用方按**协议的字段语义**选择 ✓，不能全局二选一 ✗。

    ReadStringAsync(Func<int, Task<byte[]>>, int, StringKind, Encoding)

    两段式读取的唯一编排：读头 → 按头声明补读 → 解码，并校验真的读够。

    【为什么必须收口到这一处】此前同一套编排在 DevicePro、DeviceBase、 BatchMonitor 各写一遍 ✗ ⇒ 失败口径三路不同： DevicePro 返回失败 ✓、BatchMonitor 返回 null + 日志 ✓、 而 DeviceBase **把"没读够"返回成 `IsSuccess = true` + 空串** ✗（静默错误）。 更早还出现过"一次读够最大长度"与"两段式"两种读法在同一路径上反复改动 ✗。

    【短读必须失败 —— 这不是新约定】✓ 本仓既有两个块读路径**已经**这么做： BatchMonitor.ExecuteReadCycleAsync 对 Content.Length < block.Length 记 MarkBlockFailure ✓；PlcValueExtractor 对"缓冲区不足"走 OnOutOfRange 并**丢弃该值** ✓。本方法把同一口径补齐到字符串读路径。

    【不抛异常】read 抛出的异常**原样向上传播**（与收口前一致 ✓）—— 各调用方本就有外层 try/catch 把它转成各自的结果类型。

    SwapBytesWithinWords(byte[], int, int)

    把 buffer 的 [start, start+length) 区间按 16 位「字」逐字交换两个字节 （元素顺序不变 ✓），等价于 HSL 的 SoftBasic.BytesReverseByWord ✓。

    【谁在用】 · **S7 WSTRING**：PLC 存大端字符、而 .NET 的 System.Text.Encoding.Unicode 按小端解 ✓； · **欧姆龙系（FINS / HostLink）**：HSL 对其全部协议设 IsStringReverseByteWord = true ✓（按字单位反转字符串）—— 见 `OmronFinsDriver` / `OmronHostLinkOverTcp` 的字符串读写 ✓。

    ⚠️ **只交换字内两字节，不改变元素顺序** ✗ —— 这与"整体 Array.Reverse"是**两回事** ✗ （后者会把元素顺序也倒过来 ✗，正是本仓曾出过的缺陷 ✓）。 奇数尾字节**原样保留**（不参与交换），避免越界 ✓。

    TryParseLayout(byte[], int, int, StringKind, Encoding, out int)

    同 ParseLayout(byte[], int, int, StringKind, Encoding)，但额外输出该字符串从 startIndex 起占用的总字节数 （含头），供"先读头 → 再按长度补读内容"的路径决定补读长度。

    【为什么需要它】此前每条两段式路径各自算一遍补读长度： actualLen + 2、wActualChars * 2、wActualChars * 2 + 4 —— 对"头要不要计入"出现了三种理解 ✗，其中两处还把 wActualChars * 2 直接 (ushort) 窄化 ⇒ PLC 头声明越大回绕越离谱 ✗。把"布局 → 总占用字节数"与 "布局 → 字符串"放进同一处，二者不可能再分叉 ✓。

    返回 false 表示该布局在给定缓冲下不成立，调用方须按"明确失败"处理， 不得退化成"读 1 字节再看看" ✗。
