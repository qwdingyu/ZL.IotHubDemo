    EndianConverter

    字节序转换器 — 欧姆龙 FINS 使用 CDAB（每 16 位字内高低字节交换，跨字低字在前）✓。

    🔴 【2026-10-18 修复，docs/415】原声明为 BigEndianConverter ✗ —— 那是**错的** ✗。依据（用户指定：无官方证据时**以 HSL 为参考** ✓）： HSL `OmronFinsNet` 显式设置 ByteTransform = new RegularByteTransform(DataFormat.CDAB) ✓， 且 **HSL 对全部欧姆龙协议统一如此** ✓ （`OmronFinsNet` / `OmronFinsUdp` / `OmronHostLink` / `OmronHostLinkCMode` 均同 ✓）。

    【实测证据（HSL 与自研连同一模拟器，裸字节对比）】✓ 

    Int32 123456789 (0x075BCD15)：
  自研写 → 线上 07 5B CD 15   ← 大端 ✗（与 HSL 不符）
  HSL 写 → 线上 CD 15 07 5B   ← CDAB ✓
  ⇒ HSL 读自研写的数据得 -854259877 ✗（字节被重新解释）

    【为什么用 CdabEndianConverter 而不是新写一个】本仓**已有**该转换器 ✓， 且它已在 **Fatek** 交叉测试中被验证（`FatekCrossTest` 21/21 通过 ✓， 其注释写明"自研以每字 {hi,lo} 缓冲（配 CdabEndianConverter）"✓） ⇒ 语义正是"每字内交换 + 跨字低字在前" ✓，与 HSL 的 CDAB 一致 ✓。

    ⚠️ 这是**行为变更** ✗：所有 FINS 数值读写都会改变 ✗ —— 判据是"与参考实现/现场上位机一致" ✓，而非"与自己的旧版本一致" ✗。

    SendAndReceive(byte[])

    发送一条 FINS 命令并收响应。

    Declaration
    protected virtual DeviceResult<byte[]> SendAndReceive(byte[] command)
    Parameters
    Type Name Description
    byte[] command

    命令帧。两种形态都接受 ✓：

    • 完整 FINS/TCP 帧（`BuildReadCommand`/`BuildWriteCommand` 产出，含 16 字节 TCP 头）⇒ 原样发送
    • 裸命令（`Run()`=`{4,1,255,255,4}`、`Stop()`=`{4,2,255,255}`、`ReadCpuTime()`=`{7,1}`） ⇒ 自动补 FINS/TCP 头后再发 ✓
    Returns
    Type Description
    DeviceResult<byte[]>
    Remarks

    🔴🔴 【2026-10-22 修复：裸命令曾被直接 _socket.Send ⇒ 帧不完整 ⇒ 必然超时】✗

    【原缺陷】本方法原为 _socket.Send(command) —— 直接把入参当整帧发 ✗ 而 Run()/Stop()/ReadCpuTime() 传的是裸命令（2~5 字节，无 TCP 头、无 FINS 头）： · Run() ⇒ { 4, 1, 255, 255, 4 } · Stop() ⇒ { 4, 2, 255, 255 } · ReadCpuTime()⇒ { 7, 1 } ⇒ 发出去的是残缺帧（FINS/TCP 要求 FINS|length|command|error|FINS头|MRC/SRC） ⇒ 服务端按"帧不完整"处理（不回应或断开）⇒ 我方一律超时 ✗ ⇒ 实测：对仿真器 ReadCpuTime() ⇒ 通信失败: Operation timed out ✗ （而手工组好整帧再发 ⇒ 正常返回时钟 ✓ —— 证明缺陷在本方法，不在服务端）

    【为什么长期没发现】 Run()/Stop()/ReadCpuTime() 三个入口此前零测试覆盖 ✗ （grep -rn "Run()\|Stop()\|ReadCpuTime()" tests/ 全为空） ⇒ 缺陷被"仿真器/PLC 不响应"的表象长期掩盖 ✗

    【修法】按首 4 字节是否为 ASCII "FINS" 判断形态： · 是 ⇒ 已含 TCP 头 ⇒ 原样发 ✓ · 否 ⇒ 裸命令 ⇒ 补 16 字节 TCP 头 + 10 字节 FINS 头后再发 ✓ ⚠️ 这样两种调用方式都成立，且不改变 BuildReadCommand/BuildWriteCommand 的既有行为 ✓ ⚠️ 不要改成"要求调用方自己组帧"—— 那会把复杂度推给三层调用点，且历史调用点未改 ✗

    WriteCpuTime(DateTime)

    写入 CPU 时钟（FINS 07 02）。

    官方 OMRON W342-E1-15 §5-3-20（PDF 198 页）：命令体 = 07 02 + 年(2 位 BCD)/月/日/时/分/秒/星期（各 1 字节 BCD）；响应只有 MRC/SRC + EndCode。 星期：0=周日 … 6=周六。

    ⚠️ 年份只发**两位**：官方规定 1998/1999/2000 ⇒ 98/99/00，2096/2097 ⇒ 96/97， 因此 **1996 与 2096、1997 与 2097 在协议上不可区分**。本入口只接受 1998..2097，超出即拒绝，不猜测世纪。

    【未验证】未在真实 NJ/NX/CJ 硬件核对；仿真器写入后可由 07 01 读回。
