    Class TagValueChange

    点位值变化事件载体——当某个 Tag 的值发生变化时，通过事件总线分发给订阅者。

    在工控场景中，"变化推送"（Change-of-State / CoV）是减少数据流量的核心策略： 只有当值真正发生变化时才通知上层（MES/SCADA/HMI），避免每个采集周期都推送大量未变化的数据。

    与 TagValue 的区别：TagValue 是"当前值快照"， TagValueChange 是"变化事件"，携带 TagId 和 TagItem 元数据， 便于订阅者直接定位到具体点位定义。

    Sequence

    进程内单调递增序号（2026-11-11 按 docs/652 契约新增）。

    🔴 **为什么必须有**：`docs/652` 已定调「`TagChanges` 是**设备控制信号**、**必须不丢**」。 而"不丢"在**批次层**（进程内）的唯一可执行实现是「有界内存 ＋ **溢出落盘** ＋ 按 seq 截断」—— 截断必须知道"确认到哪一条"，**没有序号就无法截断** ✗ （这正是 `TriggerSpool` 此前"只进不出"的根因：`TagValueChange` 无序号 ⇒ `Compact` 结构上驱动不了）

    Timestamp

    变化发生的时间戳。

    🔴🔴【2026-11-10 **A-287**】**基准：UTC**（`DateTimeKind.Utc`，默认 `DateTime.UtcNow`）✓

    **为什么是 UTC**：本字段在**真实采集路径**上恒被赋成 `TagValue.Timestamp` （`DeviceRoot` 的 `changes.Add(new TagValueChange { … Timestamp = newTv.Timestamp })`）， 而 `TagValue.Create*/CreateGood` 用的是 **`DateTime.UtcNow`** ⇒ **实际值一直是 UTC** ✓

    🔴 **改前缺陷（A-287）**：默认值写的是 `DateTime.Now`（**本地**）✗ ⇒ **同一字段两种基准**：真实路径是 UTC、默认值是本地 ✗✗ ⇒ 实测 `tools/OpcUaCrossCheck` 与大量测试**不显式赋值** ⇒ 拿到**本地时间** ⇒ 一旦与 UTC 比较（如 OPC UA `SourceTimestamp`）就**差一个时区** ✗

    **正确用法**： · 展示 ⇒ `Timestamp.ToLocalTime()`，不要直接格式化（否则 UTC 服务器显示成 UTC 时间）✓ · 算耗时/比新鲜度 ⇒ 直接相减（同基准）✓ · 对接 MES/Historian ⇒ 传 `DateTimeOffset` 或 ISO-8601 带 `Z` ✓
