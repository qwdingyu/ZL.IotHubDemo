    ScanRate

    期望采样周期(ms)。默认 0 表示跟随设备全局频率运行。 用于多速率发动机调度。

    🔴🔴【2026-11-11 按 **D3** 补**使用契约**：本值**不是"每点独立调度"**】✗→✓

    实际语义（实测）：调度粒度是**「块」**，不是「点」。

    1. 建块阶段（`PlcReadBlockBuilder.Build`）**只看 `MaxGap`（默认 200 字节），不看 `ScanRate`** ⇒ 地址相邻（gap ≤ MaxGap）的高低频点会**合进同一块** ✗
    2. 分桶阶段（`BuildPlan` 的"第3步"）取**块内 `min(ScanRate)`** 作为该块的调度频率 （注释原话：「取最小值保证高频标签不会被低频标签拖慢」）✓

    ⇒ 两个后果（必须知道）：

    • ✅ **高频点不会被低频拖慢**（块按最快的那个频率读）
    • ✗ **低频点会被高频拖着读** ⇒ **请求次数放大**。 例：`100ms` 与 `1000ms` 两点相邻合并 ⇒ 该块按 100ms 调度 ⇒ 低频点被**放大 10 倍**读取 ⇒ PLC/链路压力↑

    ⇒ 现场应对：若确有"高频点与低频点地址相邻"的场景，且 PLC/链路压力偏高， 可**调小设备配置的 `MaxGap`**（如 200 → 8）让它们**分开成块**，从而各自独立调度 ✓

    ⚠️ **勿误解为"每点独立"** —— 那需要"先按 `ScanRate` 分组、再在组内建块"， 属**建块策略变更**（会影响合并效率与请求次数），需 Owner 评估，**当前未做** ✗

    CanWrite()

    该标签是否允许写入（写入层的统一判据，5 处守卫共用）。

    🔴 **刻意做成方法而不是属性**（2026-10-30）：`TagItem` 是会被 Newtonsoft **序列化**的点表 DTO（见 `TagItemJsonCompatibilityTests`）， 属性会被写进 JSON（实测 `JsonConvert.SerializeObject` 输出含 `"CanWrite"`）⇒ **计算属性污染对外契约** ✗；方法不会被任何序列化器输出 ✓ （`ShouldSerialize*` 只对 Newtonsoft 有效、System.Text.Json 不认，故不采用）

    🔴 **白名单语义**：只有 `AccessMode == ReadWrite` 才可写；`ReadOnly` 与**任何未知/越界值** （如 JSON 的 `"AccessMode": 7`、XML 的 `AccessMode="7"`）一律**不可写** ⇒ fail-safe ✓

    🔴 **心跳/就绪（`HB`/`RO`）永远可写**：保证"按标签 Id 写握手点"不被误拦。 **如实说明（2026-10-30 复核）**：线上心跳/就绪由 `DeviceBase.HeartBeatLoop` **按地址**写入（`Device.WriteAsync(addr, …)`），**不经过**本判据 ⇒ 本例外不是心跳存活的前提； 它的价值是 ① 外部按标签写握手点 ② 将来启用 `DevicePro` 守卫路径时也不致中断 ✓
