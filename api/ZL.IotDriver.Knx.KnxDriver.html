    Remarks

    地址：<主/中/子>[:<DPT>]，例 1/2/4:9.001（详见 KnxAddress）。

    协议流程（全部有实测字节支撑，见 `docs/588` §9）：

    1. CONNECT_REQUEST（NAT HPAI×2 + CRI `04 04 02 00`）→ CONNECT_RESPONSE（通道号 + 状态 + CRD 顺序号）
    2. 每次读写 = 1 个 TUNNELLING_REQUEST（`04 | 通道 | 顺序号 | 00 | cEMI`）+ 等 **TUNNELLING_ACK**
    3. 读的响应由设备**主动**发来一个 TUNNELLING_REQUEST（cEMI 为 `L_Data.ind`/`con`）⇒ **必须回 ACK**
    4. 顺序号从 0 自增；顺序号不匹配的 ACK 一律忽略（实测抓包 ORDER 00→04 逐帧 ACK）

    UDP 语义：无连接 ⇒ 超时用**重发**（同 ModbusUdpDriver/OmronFinsUdpDriver 的成熟做法）； 一个数据报 = 一帧。

    未实现（诚实）：路由（多播）、总线监控、设备管理、DPT 除 1.001/5.001/9.001 之外的类型、重连退避。

    Remarks

    [!!] 固有宽度随 DPT 变化，故不接 SerialFixedWidthGuard（AGENTS §21.4 第 3 条 ① 的例外）

    KNX 的 DPT（数据点类型）决定宽度（1 位 / 1 字节 / 2 字节 / 3 字节 / 变长…） ⇒ 不是固定值 ⇒ "固定宽度断言"语义不适用。

    本驱动改为：按 DPT 解码后，用 `FitLeft`（整数类 DPT，左对齐补 0） 或 `Fit`（其它类，右对齐补 0 / 截断）**调整到 `length`**（见 `:229`）。

    已登记 `IsSingleValue = true`（见 `Protocols/NativeDriversPlugin.cs` 的 `singleValueKeys` 注释）⇒ 正常路径不会请求更小宽度。
