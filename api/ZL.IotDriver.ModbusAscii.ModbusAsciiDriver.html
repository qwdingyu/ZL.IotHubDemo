    EndianConverter

    字节序转换器（Modbus ASCII 使用大端序）

    Declaration
    public IEndianConverter EndianConverter { get; }
    Property Value
    Type Description
    IEndianConverter
    Remarks

    🔴 字节序契约表（2026-11-05 新增；AGENTS §22.5 要求的"值+含义+证据+判定"）

    背景：上面这条"维持 BigEndian(ABCD)"的结论**写对了，但实现没遵守** ✗ —— `ReadFloat`/`Write(float)`/`ReadDouble`/`Write(double)` 当时做的是**字交换（CDAB）** （`[c2,c3,c0,c1]` / `[raw2,raw3,raw0,raw1]`），而 `ReadInt32` 是**纯大端 ABCD** ⇒ **同一个驱动内部存在两套字节序** ✗。这正是"契约写在注释里、代码没照做"的典型。

    值含义 / 证据 / 判定
    ABCD（大端） **含义**：`3.14f` = `0x4048F5C3` ⇒ 寄存器 0 = `0x4048`、寄存器 1 = `0xF5C3`（高字在前）
    **证据①**：本类 `ReadInt32` = `c0<<24 | c1<<16 | c2<<8 | c3`（纯大端）
    **证据②**：`NativeDriverBase.ReadFloatAsync` = `EndianConverter.TransFloat`（家族 ABCD）
    **证据③**：本文件类头 `:97`（docs/418 实测结论：BigEndian）
    **证据④**：HSL 客户端默认写出的就是 ABCD（`ModbusAsciiOverTcpCrossTests` 实测）
    **判定**：✅ **本类唯一正确口径**
    CDAB（字交换） **含义**：`[c2,c3,c0,c1]`（低字在前）
    **证据**：2026-09-20 的"修复"引入，**无任何协议依据**；与上面 4 条证据全部矛盾 ✗
    **判定**：❌ **缺陷形态**（2026-11-05 已移除）

    症状（可复现）：HSL 写 `3.14f`（`40 48 F5 C3`）⇒ 我方旧实现读回 **`197391.83`**（= 把 `40 48 F5 C3` 当 `F5 C3 40 48` 解释）✗。

    为何长期潜伏：既有用例只断言"成功 / 请求 4 字节" （`ModbusAsciiReadQuantityTests`），**从未断言值**；ASCII 的 E2E 也没有 Float 用例 ✗。

    钉子测试（改动此处必跑）： ① `Drivers/ModbusAsciiFloatByteOrderUnitTests`（**PTY 帧层，零模拟器**，3 条： 写 3.14f 必须发出 `40 48 F5 C3`；回 `40 48 F5 C3` 必须读成 3.14f； 同帧 `0x4048F5C3` 的 int32 与 float 必须自洽）； ② `CrossTest/ModbusAsciiFloatByteOrderTests`（仿真器 32205 寄存器级往返）； ③ `CrossTest/ModbusAsciiOverTcpCrossTests`（**HSL 裁判**双向 Int16/Float）。

    变异自证（2026-11-05 实测，worktree 内完成）： 读侧恢复 CDAB ⇒ **2 红**；再注入写侧 CDAB ⇒ **3 红**； `melsec-a1e` 注册回退 3E ⇒ **1 红**（`docs/583` §8.4）。

    复核命令：dotnet test tests/ZL.IotHub.Tests -f net8.0 --filter "FullyQualifiedName~ModbusAsciiFloatByteOrderUnitTests"
