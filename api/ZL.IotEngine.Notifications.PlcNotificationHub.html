    Class PlcNotificationHub

    PLC 实时通知中枢 —— 工控数据采集与上位系统之间的核心事件分发枢纽。

    在工业现场，采集侧（`DeviceRoot`；原 `BatchEngine` 已于 `24bfaaba` 删除）周期性从 PLC 读取标签数据， 产生"标签值变化"和"连接状态变化"两类事件。本中枢负责：

    1. 事件发布与分发：接收采集侧事件，按序号排序后分发给所有活跃订阅者（SCADA/MES/UI）。
    2. 有限窗口回放（Replay）：新订阅者建立时，可立即回放最近 N 条事件，解决 UI 打开时的"冷启动"问题。
    3. 消费位点跟踪（Ack）：下游消费者通过 Acknowledge 报告消费进度，支持断点续传场景。
    4. CatchUp 追赶机制：订阅建立期间到达的新事件先缓冲，回放完成后按序排空，保证"无重复、无乱序、无窗口丢失"。
    5. 可观测性指标：提供完整的运行指标快照，用于现场诊断和监控告警。

    🔴🔴【**使用契约 —— 必读，选错路径会导致设备误动作**，详见 docs/649】

    本类投递的事件是「变化通知」，不是「控制信号源」 ✗

    实时控制 / 闭环 / 联锁判定 **读当前值**：GetLatestSnapshot() 或设备侧 DeviceRoot.GetTagValue()（走 localCache）。 事件只当「有变化，该去读一次」的**唤醒信号** ✓
    🔴 **禁止**把事件回调里的值当作控制决策的**唯一输入** —— 本类通道是**有界 ＋ DropOldest** （设计见 docs/07 §6、审查见 docs/604 §3.2），慢消费者会**丢中间值**； 而控制决策**必须基于当前物理状态** —— 一条 3 秒前的「到位=true」若被重放/延迟使用， 机械早已离开 ⇒ **夹空/撞机** ✗✗
    SCADA / HMI 展示 同样**以缓存读为准**（docs/252 的"缓存优先"），事件用于**触发刷新** ✓
    允许丢中间值：下一次读/快照会校正画面 ✓
    MES / 追溯 / 历史 **不要用本类事件流承载历史** ✗ —— 平台**刻意不内置历史存储**（docs/07 §7）， 请由消费侧落库（如 SqlSugar）或接外部 Historian ✓
    报警 / 联锁 / 扫码触发（Trigger） 这是**唯一**需要「一条都不丢」（at-least-once）的场景 ✓ ⇒ 必须走**持久化**：`PlcEventDispatcher.TriggerSpool`（docs/649 P1，**2026-11-10 已实现**） —— 队列满时落盘而非丢弃（at-least-once）；**默认关闭**，需显式启用 ✓ 不能只依赖内存通道 ✗
    上位机 → PLC 命令写入 用 WriteAsync/SendCommand：**同步 ＋ 超时 ＋ CommandId 幂等** ✓ 无队列、不重放 ✓

    一句话：控制与显示都**读当前值**，事件只是「有变化」的通知； 只有 Trigger 需要「每条都不丢」，而它必须走持久化；历史放外部 ✓

    线程安全：本类设计为完全线程安全，支持多线程并发发布和订阅。 采用单例模式（Instance），确保全局只有一个事件分发点。

    SyncActiveTags(IEnumerable<string>)

    【已废弃，多设备场景会误删他设备快照】按"活跃集合"清理全局 _latestByTag。

    🔴🔴【2026-11-11 修 B1】**这是本仓一个真实的生产缺陷**（实测复现，见 SnapshotLifecycleMultiDeviceTests.多设备重建计划_不得清掉其他设备的快照）： 本方法遍历的是**进程级全局**字典 `_latestByTag`，而入参只是**调用者本设备**的 `Tags.Keys` ⇒ 同进程多设备（`DeviceManager` 是静态注册表，天然多设备）时： 设备 B 因重连/自愈/热改点表重建计划 ⇒ 用 B 的集合清掉 A 的**全部**快照 ✗ ⇒ A 中值不再变化的点位**永不回写**（快照只在值变化时更新） ⇒ `ScadaHub.OnConnectedAsync` 下发的冷启动快照"少设备、缺点位"，**且无任何告警** ✗。

    请改用 SyncActiveTags(IEnumerable<string>, string)（带设备作用域）。 本重载**保留**仅为二进制兼容：它现在**只清理"无归属"条目**，绝不触碰有归属的快照 （即不再具备跨设备误删能力），因此也不会再造成上述故障。

    SyncActiveTags(IEnumerable<string>, string, long)

    【推荐】按设备作用域同步活跃标签集合，只清理本设备拥有的幽灵快照。

    判定规则（三条，必须同时看清）： ① 在 activeTagIds 中的键 ⇒ **永不删除**（本设备仍在采它）； ② 归属等于 deviceId 且不在活跃集合中 ⇒ **删除**（本设备已删该点）； ③ 归属是**其他设备**或**无归属** ⇒ **永不删除**（不属于本设备的清理范围）。

    `deviceId` 为空 ⇒ 退化为"只清理无归属条目"（即旧重载的兼容行为，不再跨设备误删）。

    ✅ **同名 TagId 已不再是边界**（2026-11-11 D1 根治）：快照键是复合键 `(DeviceId, TagId)` ⇒ 两台设备的同名标签**各自独立成条**，归属由 DeviceIdOfKey(string) 从键里精确取出 ⇒ 规则 ②③ 对**每一条**都成立， 既不会漏删、也不会误删他设备（原 `_tagOwner` 只记得住"最后一个发布者" ⇒ 会漏/会误，已删除）。
