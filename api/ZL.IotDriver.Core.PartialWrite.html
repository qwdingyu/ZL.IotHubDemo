    Class PartialWrite

    [][][*] 分片写的"部分写入"披露（2026-11-16 建立，解决"多帧写非原子"这一结构性问题）。

    【问题的本质（不是 bug，是协议限制）】多数 PLC 协议（Modbus FC16/FC15、S7、FEnet、 EasyNet、Memobus、FX-Links、Keyence、Cimon、HostLink …）**单帧有长度上限且没有事务语义**。 因此"一次逻辑写超过单帧上限"**物理上不可能原子**： 第 k 帧失败时，前 k-1 帧已在 PLC 生效且**无法回滚**。

    ⇒ 既然**不可能**让它原子，唯一的彻底做法是让**"部分写入"结构上不可能被忽略**：

    1. **可预知的失败全部前置**到第 1 帧之前（长度、地址范围、片边界校验）；
    2. **任何**中途失败都必须由本类生成**显式披露**的文案（含"已写 X/Y 字节、N 帧"）；
    3. `IPlcDevice.WriteBytesAsync` 的契约写明这一点（见该接口 XML 注释）。

    【为什么用一个共享类，而不是每个驱动各写一句话】文案必须**格式统一**， 否则调用方无法可靠识别"这是部分写入"。单点定义也保证**新增分片驱动时不会漏写**。

    【复核命令】 

    grep -rn "PartialWrite.Fail" ZL.IotDriver --include=*.cs | wc -l   # 应等于分片驱动数

    Remarks

    [!!][!!] 【2026-11-16 全局结构性修正】本方法不再接受 appliedFrames， 改为接受 perFrameUnits 并在内部算帧数。

    **为什么必须这样改**（不是风格问题，是缺陷类）： · 原签名要调用方手工算 `frames`，而**算它所需的常量就在手边**； · `applied / total / frames` **全是 `int`** ⇒ **编译器无法拦截参数串位**； · **实证**：2026-11-16 第 22 轮，**4 处**把字节数当帧数传了进去 （文案会写"已写 540/2000 字节（**540 帧**）"，实为 1 帧）， 而**编译通过、3187 条测试全绿** —— 因为没有断言约束这些参数。

    **改后**：调用方传的是**它本来就在用的分片常量**（与循环里的 `+= MaxChunkBytes` 同源）， 帧数由本方法 `applied / perFrame` 得出 ⇒ **"字节 vs 帧"混淆在结构上不可能再发生** ✓

    **不变式**：`appliedUnits` 恒为 perFrameUnits 的整数倍 （只有**整片成功**才累加；失败的那片不计入）⇒ 整除**无舍入误差** ✓

    DescribeChunkFailure(string, string, int, int, int, string, string)

    [*] 分片写失败披露（合并入口） —— 调用点只需一次调用，不必自己写 applied == 0 ? A : B。

    【为什么要这个合并入口】分片点在**失败分支**里，若每个点都写三元表达式， 调用处会膨胀 7~8 行；而本仓对**文件代码行数有基线约束**（`check_file_size`）。 把分支收进本方法后，调用点只需 **2 行**（`if (!r.IsSuccess)` + `return Fail(...)`）。

    【语义】`appliedBytes == 0` ⇒ 第 1 帧即失败（PLC 未改变，可安全重试）； 否则 ⇒ 已部分写入（PLC 可能处于**混合状态**，需核对）。见 Describe(string, string, int, int, int, string, string) 与本方法。

    【证据等级：N/A】同上（内部工具类）。
