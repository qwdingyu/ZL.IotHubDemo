    Class PlcStringWriteGuard

    Raw 字符串写入的容量守卫。

    【为什么单独成类】仓内共有 6 处带 maxLength 的 Raw 写入点： NativeDriverBase.WriteString/WriteStringAsync、 SiemensS7Driver.WriteString/WriteStringAsync（该类直接实现 IPlcDevice，不派生自 NativeDriverBase）、 PlcDeviceStringWriteExtensions.WriteStringFallback/WriteStringFallbackAsync （服务 AB / 三菱等“裸字驱动”，直接 device.Write(byte[]) ⇒ 绕开前两者）。 若逐点各写一遍判定，阈值与提示语迟早漂移、且新增第七个写入点时极易漏判 ⇒ 统一收口到这里，判定规则与提示语只有一处定义。

    【缺陷背景】BuildRawPayload(string, Encoding, int) 的契约是 “不截断超长，由调用方决定 Fail 或截断”，而上述 6 处原先都没有判定； NormalWriteRequest.StringLength/SafetyWriteRequest.StringLength 对外文档是 “字符串最大长度（字节/字符）”，且 tag.Length 就是字段字节宽 （读侧 ReadString(addr,size) 走 ReadBytes(addr,size)；写侧短则补零到该长度） ⇒ 超长时按实际字节数写入会写穿点表 Length 界定的字段，静默覆盖其后相邻的 PLC 存储区。 兄弟路径 S7 STRING / WSTRING 一直是超长即 Fail ⇒ 本类把同一约定补齐到 Raw 路径。

    【为什么不把判定做进 PlcStringWriteHelper】该类是“平台无关的纯函数”集合， 不应反向依赖 DeviceResult；故“纯函数只负责算、是否可写由本类判定”。

    TryBuildS7StringPayload(string, Encoding, int, out byte[], out DeviceResult)

    构建西门子 S7 STRING 负载并判定是否可写（容量判定与构造共用同一个容量）。

    【为什么需要它】原实现把"超长判定"放在驱动里、用**调用方传入的 maxLength** ✗， 而构造时 ResolveS7Capacity 会把容量**静默钳到 254** ⇒ 点表 Length = 300、内容 270 字节时：判定 (270 > 300) 通过、 构造却按 254 截断 ⇒ **静默丢 16 字节** ✗。现在判定与构造同源 ⇒ 不可能分叉 ✓。

    TryBuildS7WStringPayload(string, int, out byte[], out DeviceResult)

    构建西门子 S7 WSTRING 负载并判定是否可写。

    【为什么需要它】WSTRING 前导头的容量字段是 **16 位「字」** ⇒ maxChars > 65535 时头会**静默回绕** ✗（实测 65536 ⇒ 头声明 0 = WSTRING[0]）， 且 payload 被分配成 maxChars*2+4 字节 ⇒ maxChars = 100000 时会往字段外写 **128KB+** ✗（灾难）。现在越界即明确失败 ✓。
